# Diff Overlay 一锤子 Commit + Push

> **文档定位**：**活 spec**（会随实施反复更新）。
> 「关键决策与未决项」表是唯一真相源；正文引用它、不复述它。

## 0. 一页纸（骨架先行）

- **一句话**：在已有的未提交 diff Overlay 上增加「提交并推送」：看完改动后一锤子 `add -A` → AI 草稿 message（可改）→ `commit` → `push` 当前分支，免开终端。
- **承重决策**（3~5 条）：
  1. **确认弹窗一锤子（方案 A）** —— 不做原子控制面板/两段确认，因为动机是 agent 改完看一眼就提交（详见 §3 / 〈决策·one-shot-modal〉）。
  2. **固定 `git add -A`** —— 含未跟踪与删除；弹窗写死说明，不做分文件 stage（详见 〈决策·add-all〉）。
  3. **AI message + 人确认** —— llm-proxy 生成草稿，textarea 可改；无「重新生成」按钮；空 message 不可提交（详见 〈决策·message-editable〉）。
  4. **commit + push，无危险写** —— 不做 reset、force push、改历史；push 不自动 `--set-upstream`；**ff-only pull / behind 闸门**另见 `plan/20260719.git-pull-when-behind.md`（详见 〈决策·no-dangerous-git〉〈决策·no-auto-upstream〉〈决策·write-path-scope〉）。
  5. **全成功才关 Overlay** —— commit 与 push 都成功则关闭 Overlay 并刷新 dirty；任一步失败（含 commit✓ push✗）留在确认层展示分步结果（详见 〈决策·close-on-full-success〉）。
- **验收总目标**：dirty Overlay 可完成一次本地提交并推送到当前分支上游；用户始终清楚 add-all 与部分成功含义；无白名单外路径、无危险 git 参数；提交流程不断开 SSE。

## 1. 需求背景

### 1.1 原始需求

> 给项目的 git 预览功能增加：点击 diff 之后可以进行 diff 的预览，顶部展示提交按钮；点击后弹窗，后端 pull、add all、生成 commit message、提交。也可做成 pull / add / generate / commit / push 的原子控制面板。交互未定。

后续确认：动机是 Agent 改完文件后不想开终端；MVP 为 **commit + push**（不做 pull）；`git add` 范围全部且需说清；message 由 AI 生成并给人二次确认；push 默认当前分支；不做 reset / force push / 改历史；心智是看完 diff 一锤子提交。选定方案 A。补充：push 不自动 set upstream；不要重新生成按钮；全成功后关闭 Overlay。

### 1.2 背景与动机

Diff Overlay（`plan/20260717.git-diff-overlay.md`）已解决「边聊边看 agent 改了什么」，但仍是只读。用户核对后仍要切终端做 add/commit/push。本需求把核对与提交收在同一 Overlay 路径里。

### 1.3 目标与验收标准

- Overlay 顶栏有「提交并推送」；确认层写明 add-all 与目标分支；message 可编辑。
- 全成功：本地有 commit、已 push、标题栏 dirty 更新、Overlay 关闭（〈决策·close-on-full-success〉）。
- 部分成功 / 失败：分步结果可见，不误导；不自动 rollback（〈决策·partial-success〉）。
- 安全边界按 〈决策·no-dangerous-git〉〈决策·cwd-allowlist〉〈决策·keep-stream〉。

### 1.4 约束与前提

- 前端仍是无构建单页；能力落在 `public/` + Express API。
- 写操作仅允许 `config.json` 白名单 cwd（与现有 git 只读 API 同源，详见 〈决策·cwd-allowlist〉）。
- 推翻上一版 Overlay 的「只读 MVP」边界：本功能是明确的写路径；仍不做 discard/分文件 stage；pull 范围以 〈决策·write-path-scope〉 及 `plan/20260719.git-pull-when-behind.md` 为准。
- message 生成走本机 llm-proxy，不走 `@cursor/sdk` Agent（与标题同因：避免脏写会话历史，详见 〈决策·message-via-gateway〉）。
- 易变阈值（diff 截断喂给 LLM 的上限、超时、API 字段名）收口 §5，正文不复述多份。

## 3. 方案设计

### 方案 A：确认弹窗一锤子（选定 / 推荐）

- **思路**：Overlay 顶栏「提交并推送」→ 确认 modal（add-all 说明、分支、文件数、可编辑 AI message）→ 一次 `commit-and-push`。后端拆「生成 message」与「commit+push」两接口，UI 仍是一条路径——改文案不必重跑 git，且生成失败可手填。
- **改动范围**：见 §2.4。
- **优点**：贴合「看完就提交」；说明集中；实现量可控。
- **缺点/风险**：部分成功需专门结果态（已纳入 〈决策·partial-success〉）。
- **工作量**：M

### 方案 B：原子控制面板（未选）

分步按钮（generate / commit / push）。对无 pull、固定 add-all 的 MVP 过重。

### 方案 C：两段确认（未选）

先 commit 再确认 push。多一步，与一锤子动机略冲。

### 方案对比

| 维度 | A | B | C |
|------|---|---|---|
| 贴合一锤子 | 最好 | 差 | 中 |
| 部分成功表达 | 需结果态 | 天然 | 天然 |
| 工作量 | M | L | M |

### 最终选定

**方案 A**，用户 Phase 3 选定。补充约束见 §5〈决策·no-auto-upstream〉〈决策·no-regenerate〉〈决策·close-on-full-success〉。

### 执行步骤

原则：**可失败的 AI 生成前置；不可逆 git 写殿后；一次写接口返回分步结果，禁止静默 rollback。**

1. **commit message 服务** —— 按 cwd 取未提交 diff 文本（复用/抽取 `gitDiff` 能力），按 〈决策·message-truncation〉截断后调 llm-proxy；失败返回 `null`（调用方手填）。不走 Agent（〈决策·message-via-gateway〉）。
2. **git 写模块** —— 固定序列：`git add -A` → `git commit -m <message>` → `git push`（当前分支，无额外 force/上游参数）。每步记录 ok + 错误摘要；commit 失败则不 push（〈决策·partial-success〉）。
3. **HTTP** —— `POST /api/git-commit-message`、`POST /api/git-commit-push`；cwd 白名单（〈决策·cwd-allowlist〉）；不接受客户端任意 git args。
4. **确认 modal** —— Overlay 顶栏按钮；打开时请求 message 草稿；无重新生成（〈决策·no-regenerate〉）；主按钮在 message 非空且未提交中可点；文案写明 add-all（〈决策·add-all〉）。
5. **结果与收尾** —— 全成功：关 Overlay + `refreshGitDirty`（〈决策·close-on-full-success〉）；否则留在 modal/Overlay 展示分步结果；全过程不 `detachStream`（〈决策·keep-stream〉）。
6. **typecheck** —— `npm run typecheck`。

### 压力测试

| 压力维度 | 具体场景 | 方案表现 | 是否需要防御性设计 |
|----------|---------|----------|------------------|
| 故障容错 | llm-proxy 失败 | 不阻断提交 | 是：手填 message |
| 故障容错 | commit✓ push✗ | 本地已有 commit | 是：分步结果 + 不 rollback（〈决策·partial-success〉） |
| 故障容错 | 无 upstream | push 非零 | 是：回传错误；不自动 `-u`（〈决策·no-auto-upstream〉） |
| 并发 | 连点提交 | 双 commit 风险 | 是：UI 锁；后端按 cwd 拒绝并发写（或等价串行） |
| 规模 | 超大 diff 喂 LLM | 超时/劣质 message | 是：〈决策·message-truncation〉 |
| 操作风险 | agent 仍在改文件 | 提交内容 ≠ 刚看的 diff | 是：确认文案「以确认时工作区为准」；提交中禁用；成功后刷新 |
| 外部契约 | git CLI 失败形态 | stderr 需可读 | 是：实施前用脏仓库验证 add/commit/push 失败输出并回写 §5 |

## 4. 实施计划

### 4.1 子任务拆解

| # | 任务 | 涉及文件/模块 | 验收标准 | 优先级 |
|---|------|---------------|----------|--------|
| 1 | commit message 服务 + 截断 | 新 `src/*`（类 titleService）、可选复用 gitDiff | 按 〈决策·message-via-gateway〉〈决策·message-truncation〉；失败返回 null | 必须 |
| 2 | git 写模块（add→commit→push） | 新 `src/gitCommit.ts`（名可调） | 分步结果；无危险参数；按 〈决策·no-auto-upstream〉 | 必须 |
| 3 | 两个 POST + 白名单 | `src/server.ts` | 非白名单 403；空 message / 非 dirty 拒绝 | 必须 |
| 4 | Overlay 按钮 + 确认 modal | `index.html`、`style.css`、`dom.js`、`gitDiff.js`、`api.js` | 文案含 add-all；可编辑 message；无重新生成 | 必须 |
| 5 | 结果态与收尾 | `gitDiff.js`、`gitStatus.js` | 全成功关 Overlay 并刷新 dirty；部分成功分态展示 | 必须 |
| 6 | 回归：不断 SSE | 提交流程调用链 | 无 `detachStream` | 必须 |

### 4.2 测试要点

- [ ] dirty 仓库：生成草稿 → 改一字 → 提交并推送成功 → Overlay 关闭、dirty 消失
- [ ] AI 失败：手填 message 仍可提交
- [ ] 空 message：主按钮不可用或后端 400
- [ ] 工作区干净 / 非 repo / 非白名单：安全拒绝
- [ ] 模拟 push 失败（如断 upstream）：commit 已存在，UI 显示「本地已提交、推送失败」
- [ ] 提交过程中连点：不会发出两次成功的 commit
- [ ] Overlay/提交流程中对话 SSE 仍可用

### 4.3 首跑策略

**触发判断**：涉及本机 git **不可逆写入**（commit/push）与 llm-proxy 调用；非按量云 API 高成本，但仍需先在可丢弃的脏仓库验证。

- [ ] 用临时 git 仓库验证 add / commit / push 成功与无 upstream 失败形态，再接 UI
- [ ] message 生成先对小 diff 试通；截断逻辑用大 fixture 文本本地测，不必真 push
- [ ] 不对生产远程做 force；首次联调 push 目标应为可接受的个人分支/仓库

| 名字 | 结论 | 来源 | 影响位置（改它要动哪） |

| one-shot-modal | 方案 A：Overlay 顶栏 → 确认 modal → 一锤子 commit+push；不做控制面板/两段确认 | 用户 Phase 3 | §0、§3、任务#4 |

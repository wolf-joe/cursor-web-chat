# 日志合并里程碑与降噪

> **文档定位**：一次性交付（实施后以代码旁 `决策·` 与本表收口结论为准；不另开活 spec 迭代）。

## 0. 一页纸（骨架先行）

- **一句话**：把对话主链与旁路（标题 / TTS / commit message）的 happy-path info 收成少量里程碑，去掉字段复读与过程碎日志，提高 Supervisor 日志信息密度。
- **承重决策**：
  1. **方案 A：只改调用点** —— 不改 `logger.ts`、不加 `LOG_LEVEL`/debug，因为单用户自托管排障靠里程碑+终态/错误已够（详见 §3）。
  2. **「聊天 run 已建立」只打在 `agentService`** —— server / runHub 不再各打一条，避免同字段三连（详见 〈决策·send-milestone-agentService〉）。
  3. **租约年龄仅超龄打** —— 翻盘原「每次 send 打 age」；健康路径静默，flush warn 仍带 `ageMs`（详见 〈决策·lease-age-log〉）。
  4. **旁路成功留一条汇总** —— 标题 / commit message / TTS 去掉「开始」与过程碎条，成功各 1 条 info（详见 〈决策·side-task-success-one〉）。
  5. **SDK stdout 不管** —— `LocalCursorRulesService` 等不在本仓库 logger 内，本轮放弃过滤（详见 〈决策·sdk-stdout-out〉）。
- **验收总目标**：打开已有会话约 1 条 info；缓存命中续聊约「建立 1 + 终态 1」；冷 resume 不拆双条；标题/commit/TTS 成功各 ≤1 条 info；健康 send 无租约年龄 info；`npm run typecheck` 通过。

## 1. 需求背景

### 1.1 原始需求

> 打开一个窗口，然后进行聊天，感觉打印了很多日志啊。日志是否可以优化一下？保留核心的信息，同时提升信息密度。

后续确认：也要压 TTS、标题、commit message；合并里程碑 + 降噪；SDK 放弃管理；租约硬约束改为「仅超龄 / 仅异常时打」；旁路成功仍留一条汇总；git 模块本轮不动。

### 1.2 背景与动机

自托管靠 Supervisor 日志排障。当前一次「打开会话 → 续聊」happy path 可达十余条 info，且 `cwd` / `agentId` / `model` 几乎每条复读，信噪比低，淹没真正有用的终态与错误。

### 1.3 目标与验收标准

- [ ] 打开已有会话：约 1 条 `会话已加载`（含 runCount / liveRun）。
- [ ] 热缓存续聊：1 条 `聊天 run 已建立`（`cache:hit`）+ 1 条 run 终态；无「收到请求 / 发起 send / hub 开始消费 / SSE 接入」info。
- [ ] 冷 resume 续聊：建立条带 `cache:resume`，无独立的「冷启动 / resume 完成」双条。
- [ ] 新建会话：建立条带 `cache:create`；标题成功 1 条。
- [ ] 健康 send：无 `executor 租约年龄` info；超龄 flush 仍 warn（带 ageMs）。
- [ ] TTS / commit message 成功各 1 条汇总；过程碎 info 消失；失败 / 长行仍打。
- [ ] git status/diff/commit/pull 模块不改；SDK 两行可仍出现。
- [ ] `npm run typecheck` 通过。

### 1.4 约束与前提

- 只改日志文案与是否打点，不改 API / run 生命周期 / 业务行为。
- 不引入 debug 级别或 env 开关（详见 〈决策·no-debug-level〉）。
- git 业务模块已无 info，本轮只动 commit message 短任务链路（详见 〈决策·git-modules-skip〉）。
- `决策·log-run-terminal` / `决策·log-terminal-status` 保持：终态与异常 status 仍打。

## 2. 现状分析

### 2.1 相关代码/系统现状

统一出口是 `src/logger.ts`（info/warn/error + JSON context）。对话链路上：

- `server.ts`：进入会话、历史加载完成、收到聊天请求、交给 runHub 等。
- `agentService.ts`：租约年龄（每次 send）、缓存命中、冷 resume×2、发起 send、已建立 run。
- `runHub.ts`：开始消费 stream、SSE 接入（有/无 live）、run 终态。

旁路：`titleService` / `commitMessageService` 各「开始+成功」；`ttsService` 另有首 content、首句、每句合成、完成、写缓存等多条过程 info。`src/git*.ts` 自身无 `log.*`；失败只在 `server.ts` 打 error。

### 2.3 现状与目标的差距

| 现状 | 目标 |
|------|------|
| 打开会话 2 条 info | 1 条 |
| 续聊建立路径 ~8–10 条重叠 info | 1 条（+ 终态 1 条） |
| 每次 send 打租约年龄 | 仅超龄 warn |
| 标题/commit 开始+成功 | 仅成功 1 条 |
| TTS 过程 5+N 条 | 成功 1 条汇总 |
| SSE 每次接入打 info | happy path 不打 |

### 2.4 影响范围

- **修改**：`server.ts`、`agentService.ts`、`runHub.ts`、`titleService.ts`、`commitMessageService.ts`、`ttsService.ts`；`plan/20260720.auth-executor-max-age.md` 中 〈决策·lease-age-log〉；相关代码旁 `决策·` 注释。
- **不改**：`logger.ts` 形态、git 模块、SDK、前端、业务协议。

## 3. 方案设计

### 方案 A：只改调用点（选定）

- **思路**：删除或合并 happy-path 碎 info；关键节点各留一条高密度里程碑；warn/error 与 run 终态保留。
- **改动范围**：见 §2.4；「聊天 run 已建立」仅 `agentService.sendMessage` 成功路径打一次（结论一句话，详见 〈决策·send-milestone-agentService〉）。
- **优点**：无新概念、回归面小、立刻提高密度。
- **缺点/风险**：无 debug 开关，细排障需临时加 log 或另开需求。
- **工作量**：S～M

### 方案 B：加 debug 级别 + 里程碑（未选）

过程细节降 `debug`，env 控制；工作量更大，单用户场景收益有限。

### 方案 C：请求 opId 串联（未选）

并发对账更好，但本产品单用户，额外字段反而降密度。

### 最终选定

**方案 A**。用户确认：「聊天 run 已建立」只放在 `agentService`；旁路成功留汇总；git 模块跳过；SDK 不管；租约仅超龄打。

### 里程碑约定（实施时按此改）

| 事件 | 级别 | 文案（可微调） | 关键字段 |
|------|------|----------------|----------|
| 打开会话 | info | `会话已加载` | cwd, agentId, runCount, liveRun, mode |
| send 成功 | info | `聊天 run 已建立` | cwd, agentId, runId, model, mode, cache(`hit`\|`resume`\|`create`), textLen, textPreview?, imageCount |
| run 终态 | 现有 | 不变 | usage / error / durationMs 等 |
| 租约超龄 flush | warn | 现有文案 | ageMs, maxAgeMs, cachedCount… |
| 标题成功 | info | `会话标题已生成` | title, model? |
| commit message 成功 | info | `commit message 已生成` | message |
| TTS 成功 | info | `TTS 已生成` | runId, sentenceCount, bytes, durationMs |
| 取消/删/撤销/重命名/缓存淘汰等 | 保持 | 低频用户操作不收 | — |

**明确删除的 happy-path info（示例名，以代码为准）**：`进入会话`（并入加载）、`收到聊天请求`、`发起 agent.send`、`executor 租约年龄`（健康）、`agent 缓存命中`、独立冷启动/resume 完成、server 侧「交给 runHub」、`run 开始消费 stream`、SSE 有/无 live 接入、标题/commit「开始」、TTS 开始/首 content/首句/每句/单独「缓存已写入」。

### 压力测试（残余）

| 压力维度 | 具体场景 | 方案表现 | 是否需要防御性设计 |
|----------|---------|----------|------------------|
| 排障回归 | auth 中毒对照租约年龄 | 健康路径无 age；超龄 warn 仍带 ageMs | 否（已纳入翻盘后的 lease 日志） |
| 排障回归 | TTS 单句卡住 | 无每句 info；失败 error + 成功汇总仍有 | 否；句级细日志另开需求 |
| 演进 | 以后要临时细日志 | 无 debug 开关 | 接受（选 A 的代价） |
| 文档漂移 | 旧 plan 仍写「每次 send 打 age」 | 后人可能加回碎日志 | **是**：同步翻盘 plan + 代码旁注释 |

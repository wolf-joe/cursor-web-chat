# 会话进行中 run 的可接入直播 + 前端 ES 模块化重构

> **文档定位**：一次性交付。
> 所有"会随实施反复确认/可能翻盘"的结论收口在 §5「关键决策与未决项」表，正文引用、不复述。

## 0. 一页纸（骨架先行）

- **一句话**：现在 run 的事件流寄生在发起那次 `POST /api/chat` 的请求里、全进程只消费一次，所以刷新/换设备就再也接不上正在跑的直播。本质是"事件流没有独立于 HTTP 连接的归属地"——是后端架构问题，不是前端界面问题。

- **承重决策**（细节挂后文，权威结论见 §5）：
  1. **run 生命周期上移到进程内的广播中枢（hub），不再归请求处理函数**——这是唯一的结构性改动，`clientGone` 空转 hack 随之删除（详见〈决策·hub-owns-lifecycle〉）。
  2. **统一 SSE 路径**：`POST /api/chat` 改为"发起即返回"，所有客户端（含发起方）都走 `GET /api/agent/stream` 接入——单一渲染路径，最省前端心智（详见〈决策·unified-sse-path〉）。
  3. **只接实时尾巴、不回放整轮**：hub 不缓存事件流，接入者从当下起看；run 结束后靠 `/api/conversation` 补全整轮（详见〈决策·replay-tail-only〉）。为此 hub 只额外记住当前 run 的**一句用户文本**，供接入端渲染用户气泡（详见〈决策·attach-user-text〉）。
  4. **前端按原生 ES 模块拆分**，无构建器；新增的 SSE 逻辑落在独立的 `stream.js`，避免"先堆进 1200 行再返工"（详见〈决策·es-module-refactor〉）。

- **验收总目标**：同页刷新、他页、他设备中途进入一个进行中的会话，都能看到实时流式输出并停止它；停止对所有观看者生效且状态一致；ES 模块拆分后整页既有功能不回归；`npm run typecheck` 通过。

> 读完本节即掌握"做什么、凭什么这么定、怎么算成功"，后文都是补证据。

## 1. 需求背景

### 1.1 原始需求
> 目前的代码不支持"正在运行中的会话"的状态转移。在一个页面跟 AI 交互、AI 开始生成内容时，如果刷新页面，之后就再也没法从当前页面或其他页面看到这个进行中的流式输出。希望做到：在当前页 / 其他页 / 其他设备进入这个正在运行的会话时，依然能看到流式输出，并支持停止。
>
> 补充：顺带重构 `app.js`（目前 1200 行）。

### 1.2 背景与动机
单用户自托管场景下，长 run（AI 长时间生成、跑工具）期间一次误刷新或换设备，就等于"失联到 run 结束再刷新一次"才能看到结果，中途既看不到进度也无法停止。目标是让"正在跑的 run"成为可从任意入口接入、观看、中止的一等状态。

### 1.3 目标与验收标准
见 §0「验收总目标」。可判定的核心条目在 §4.2 逐条列出。

### 1.4 约束与前提
- 进程内内存广播，不引外部依赖（Redis/队列）——静态前提，权威结论见〈决策·in-memory-hub〉。
- 无构建步骤、无前端 npm 依赖、无框架——沿用项目既定定位（CLAUDE.md）。
- 重连回放只做"尾巴"，不做整轮回放——见〈决策·replay-tail-only〉。

## 2. 现状分析

### 2.1 相关代码现状
- **run 生命周期寄生在 HTTP 请求里**：`server.ts` 的 `/api/chat` 内 `for await (const event of run.stream())` 这一个循环，同时负责消费事件、写响应、并在 `finally` 里 `clearBusy` + `res.end`。"跑完一个 run"在代码里是**请求处理函数的副作用**，没有独立生命周期；`clientGone` 标志靠"请求"硬撑"run"，断连后空转到底。
- **`run.stream()` 全进程只消费一次**，事件只 `res.write` 给发起那次请求的那条响应，没有"第二个订阅者"的概念。
- **"有无进行中 run"这个事实只活在内存私有字段**：`agentService` 的 cache entry 有 `busy` + `currentRun`，但对外只有 `isAgentCached`（查句柄在不在），查不到 busy 状态。
- **历史接口与直播完全隔离**：`/api/conversation` 只吐 `status==="finished"` 的 run（`history.ts`），与当前这条"活"的 run 无交集。

### 2.2 现状与目标的差距
| 能力 | 现状 | 目标 |
|---|---|---|
| run 事件消费者数量 | 恰好 1（发起方响应） | N（任意接入） |
| run 生命周期归属 | HTTP 请求的副作用 | 独立于连接的服务端对象 |
| "有无进行中 run"可查询 | 否 | 是（接入端/历史端可问到） |
| 接入进行中 run | 无入口 | 一个可接入的 SSE 端点 |

### 2.3 影响范围
- **新增** `src/runHub.ts`：run 生命周期 + 订阅者扇出的归属地。
- **`src/server.ts`**：`/api/chat` 改"发起即返回"；新增 `GET /api/agent/stream`(SSE)；`/api/conversation` 附 `liveRun` 标记；删 `clientGone`。
- **`src/agentService.ts`**：`sendMessage` 把 run 交给 hub（不再返给请求消费）；新增查 live run 的入口；`cancelRun` 不动。
- **`src/titleService.ts` 集成点**：标题改为经 hub 广播 `title` 事件。
- **`public/app.js`**：拆成 ES 模块 + 接入改造；`handleStreamEvent` 事件分发原样复用（事件形状不变）。
- **`src/history.ts`**：不动（仍 finished-only；`liveRun` 检测是独立路径）。
- **`public/index.html`**：`app.js` 的 `<script>` 改 `type="module"`（一处）。

## 3. 方案设计

### 方案 A：run-hub + 统一 SSE（选定）
- **思路**：`POST /api/chat` 只发起、立即返回 `{agentId}`；所有客户端（含发起方）走 `GET /api/agent/stream`(SSE) 接入 hub。全站一条渲染路径。
- **改动范围**：新增 `runHub.ts`；改 `server.ts` 三处端点；前端接入统一走 SSE。
- **优点**：发起方与旁观者同一套逻辑，前端心智最省；EventSource 自带断线重连。
- **缺点/风险**：发起方"发出后再开 SSE"，首字节延迟略增（单用户可忽略）。
- **工作量**：M。

### 方案 B：run-hub + 混合双入口
- **思路**：`POST /api/chat` 仍把发起方那条流直接写回，同时喂 hub；只有旁观/刷新走 SSE 接入。
- **缺点/风险**：两套渲染入口（NDJSON + SSE）并存；发起方刷新时要从"POST 流"切到"SSE 接入"，状态迁移最绕；hub 要同时伺候内联发起方与外部订阅者，生命周期更复杂。
- **工作量**：M~L。

### 方案 C：WebSocket 单通道
- **思路**：发送、接入、停止、事件全走一条 WebSocket。
- **缺点/风险**：引入 `ws` 依赖 + 自写连接/重连管理；与现有"POST + NDJSON"体系全换；对单用户属过度工程。
- **工作量**：L。

### 方案对比
| 维度 | A 统一 SSE | B 混合双入口 | C WebSocket |
|---|---|---|---|
| 渲染路径 | 1 条 | 2 条 | 1 条 |
| 前端复杂度 | 低 | 高 | 中 |
| 后端复杂度 | 低 | 中 | 高 |
| 断线重连 | 自带 | 半边有 | 手写 |
| 新依赖 | 无 | 无 | ws（违背定位） |

### 最终选定
**方案 A**。理由：把发起方和旁观者收敛成同一条路径，恰好正面回应"前端复杂"的顾虑；B 表面省事实则制造两套入口 + 一个最绕的状态迁移；C 过度工程。前端重构方式选**原生 ES 模块**（见〈决策·es-module-refactor〉）。

### 执行步骤
总原则：**后端先立 hub 骨架再改端点；前端先纯搬运验证再叠加行为**——把"移动代码"与"改变行为"分离，回归好定位（见〈决策·refactor-then-behavior〉）。

后端：
1. **新建 `runHub.ts`**：把 `run.stream()` 消费循环从 `server.ts` 搬进来，成为独立生命周期——持有订阅者集合、当前 run 的用户文本（〈决策·attach-user-text〉）、终态宽限计时（〈决策·terminal-grace〉）、`done` 时 `clearBusy`。*先做，后续全依赖它存在。*
2. **`agentService.ts`**：`sendMessage` 建立 run 后交 hub 托管；新增 `getLiveRun(agentId)` 查询；`cancelRun` 不动。
3. **`server.ts`**：`/api/chat` 改"发起即返回 `{agentId}`"；新增 `GET /api/agent/stream`(SSE) 订阅 hub，并对"已无 live run 且过宽限期"的接入返回明确终止信号（〈决策·sse-close-on-terminal〉）；`/api/conversation` 附 `liveRun`；删 `clientGone`。
4. **`titleService` 集成点**：标题改经 hub 广播。

前端：
5. **按原生 ES 模块拆分（纯搬运，行为不变）**：拆为 `state / api / render / sidebar / models / composer / stream / app`，`index.html` 改 `type="module"`；`state.js` 作为底层不 import 业务模块以避免循环引用（〈决策·es-module-refactor〉）。*先验证整页既有功能全部正常，再进下一步。*
6. **`stream.js` 接入 SSE**：把 `readNdjsonStream(POST body)` 换成 `EventSource` 接入；`handleStreamEvent` 原样复用；收到终态主动 `EventSource.close()` 并重拉 `/api/conversation` 补全整轮。
7. **发送/打开会话接线**：`sendMessage` 拿 `{agentId}` 后 attach；`openConversation` 见 `liveRun` 则 attach；`streaming`/停止按钮状态改由 attach 生命周期驱动。

### 压力测试（只留暴露了新设计点的行）
| 压力维度 | 场景 | 需要的防御 |
|---|---|---|
| 竞态 | 旁观端拿到 `liveRun=true` 后、开 SSE 前 run 就结束了 | hub 终态后保留极短宽限期，仅为向刚接入者补发一个 `done` 触发它重拉历史（〈决策·terminal-grace〉） |
| 断连重连 | 长 run 期间 SSE 断开，重连时 run 已结束 | EventSource 默认无限重连；接入端收终态须主动 `close()`，服务端对已结束的接入返回明确终止信号（〈决策·sse-close-on-terminal〉） |
| 重构风险 | ES 模块循环引用 / 某模块加载失败拖垮整页 | `state.js` 不 import 业务模块、`app.js` 只做薄装配；拆分与 SSE 分两步、先搬运后改行为（〈决策·refactor-then-behavior〉） |

> 无成本风险（不涉及付费 API / 不可逆写入），故无"首跑策略"一节。并发发送落败方保持现有 409 弹窗报错、不静默 attach（〈决策·concurrent-send-reject〉）。

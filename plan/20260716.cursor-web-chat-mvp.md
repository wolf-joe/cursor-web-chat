# Cursor Web 对话应用 MVP 方案

> **文档定位**：一次性交付（MVP 骨架）。「关键决策与未决项」（§5）是全文唯一真相源，正文引用它、不复述。

## 0. 一页纸（骨架先行）

- **一句话**：用 Cursor **TypeScript SDK 的 local 运行时**，做一个**单用户自用**的网页版 Cursor 对话器——在预定义文件夹上新建/继续对话，发文字、按事件流式看 AI 回复、渲染历史（含 thinking 与工具调用）。

- **承重决策**（细节挂到后面章节 / §5）：
  1. **只做 local 运行时** —— agent 在后端 Node 进程内联跑、直接读写选中文件夹，这与"按文件夹管理会话"的需求天然对应（详见〈决策·runtime〉）。
  2. **复用 SDK 默认 SQLite store** —— 能看到 IDE/CLI/旧脚本在同一文件夹创建的 agent，与现有 Cursor 生态打通，且历史天然持久化（详见〈决策·store〉）。
  3. **富历史走 `listRuns` + `run.conversation()`，不用 `messages.list`** —— 后者的 `message` 字段不透明、不暴露 thinking/工具；前者返回结构化步骤（详见〈决策·history-source〉）。
  4. **发消息=POST 返回 chunked NDJSON 流** —— 把活 run 的 `run.stream()` 事件逐行透传，send 与 stream 合一，单用户场景最简（详见〈决策·transport〉）。
  5. **后端维护 `Map<agentId, SDKAgent>` 句柄缓存** —— send/stream 依赖内存中活着的 agent 句柄，未命中则 `Agent.resume()`（详见〈决策·agent-cache〉）。
  6. **不开 sandbox、AI 自主操作** —— 行为同 Cursor IDE 默认，AI 会真实读写/执行选中文件夹（详见〈决策·sandbox〉）。

- **验收总目标**：
  1. 侧边栏展示预定义文件夹列表，二级目录展示每个文件夹下的会话；
  2. 点会话 → 主对话页渲染完整历史（user 文本 + assistant 文本 + thinking + 工具调用）；
  3. 新建会话或在已有会话追问 → 发文字后，AI 回复按事件流式增量出现；
  4. 多轮对话上下文自动保留（同一 agent 连续 send）。

## 1. 需求背景

### 1.1 原始需求
> 出一版正式的 Web 应用，使用 TypeScript SDK，支持用户在网页上发送文字给 AI，并渲染历史消息和当前会话的增量消息；用户可在预定义的文件夹列表里查看会话或新建会话。侧边栏展示文件夹列表并用二级目录展示会话，点击/新增会话跳到主对话页进行历史查看与文本发送。渲染按事件（不逐字），渲染 thinking 与工具调用，固定 composer-2.5 模型。

### 1.2 背景与动机
前期已用 **Python SDK** 做过探索：跑通对话（`cursor_chat.py`）、摸清默认 SQLite 存储结构（`docs/sdk_internals.md`）、做了一个**只读**的历史浏览器（`cursor_agent_viewer.py`，手工读 `run_events` 拼装对话）。本次目标是转向 **TypeScript SDK**、做成**可交互**的正式 Web 对话应用。旧 Python 脚本不复用。

### 1.3 目标与验收标准
见 §0「验收总目标」。MVP 边界：单用户、local、固定模型、文本输入（不含图片）、无取消按钮、无模型选择。

### 1.4 约束与前提
均为会随实施确认或影响全局的结论，收口到 §5，此处只点到：
- 运行时、存储、模型、使用者规模、连接方案、sandbox 开关 —— 见 §5.1 决策表。
- `CURSOR_API_KEY` 运行前必须由使用者提供（详见〈决策·apikey〉）。
- Node ≥ 22.13（本机 v22.22 已满足），SDK 版本 `@cursor/sdk@1.0.23`。

## 2. 现状分析

### 2.1 工程现状
全新工程，无 `package.json`，仅有 `docs/`（SDK 文档）与 `tmp_scripts/`（Python 探索脚本，本次不复用）。需从零建一个 Node/TS 服务：静态托管一个无构建单页 + 少量 HTTP API。

### 2.2 SDK 能力现状（决定实现路径的关键事实）
以下均以 `@cursor/sdk@1.0.23` 的 `.d.ts` 类型定义坐实，来源收口到 §5.1。

- **新建 / 恢复 / 发送 / 流式**：`Agent.create({model:{id:"composer-2.5"}, local:{cwd}})` → `agent.send(text)` → `run.stream()`（`AsyncGenerator<SDKMessage>`，事件类型含 `assistant`/`thinking`/`tool_call`/`status`/`usage`）；`Agent.resume(agentId)` 恢复会话。全部已验证。
- **列会话**：`Agent.list({runtime:"local", cwd})` 返回该文件夹下的 `SDKAgentInfo`（agentId/name/summary/lastModified/status）。
- **富历史来源**（本方案的核心取数决策）：`Agent.messages.list` 的返回项 `message` 字段是 `unknown`、只分 user/assistant，**不暴露 thinking/工具**——这正是旧 Python viewer 当年要手动读 SQLite 的根因。正确来源是 `Agent.listRuns` 枚举会话的每次运行 → 对每个 run 调 `run.conversation()`，返回的 `ConversationTurn` 步骤明确含 `assistantMessage`/`toolCall`/`thinkingMessage`。详见〈决策·history-source〉。

### 2.3 现状与目标的差距
从"只有 Python 只读浏览器 + 命令行 demo" → "TS 可交互 Web 应用"。差距集中在：① 建 Node 服务与 API；② 活 agent 句柄的生命周期管理（§0 决策 5）；③ 前端单页（侧边栏 + 主对话页 + NDJSON 流式渲染）。

### 2.4 影响范围
纯新增，不改动既有文件。`tmp_scripts/scan_cursor_agents.py` 的"路径反推"逻辑本方案**不需要**——因为改用手动预定义文件夹列表，直接用 `cwd` 调 `Agent.list`。

> 认知校准（用户设想 vs 实际分析）属过程产物，放〈附录 A〉；其得出的决策结论已上移到 §5。

## 3. 方案设计

### 3.1 总体结构
单个 Node/TS 进程，三层：

- **SDK 交互层**：封装 `Agent.*` 与句柄缓存 `Map<agentId, SDKAgent>`（未命中 `resume`）。是唯一触碰 SDK 的地方，将来接 cloud 只需扩这一层。
- **HTTP 层**：静态托管单页 + 下列 API。
- **前端单页**：无构建，一个 HTML + 原生 JS + CDN markdown 库（沿用旧 viewer 的渲染风格）。

### 3.2 API 设计（按数据流组织）
每个接口旁写清它为什么这么设计：

- **`GET /api/folders`** —— 返回预定义文件夹列表及每个文件夹下的会话（对每个文件夹调 `Agent.list({runtime:"local", cwd})`）。侧边栏一次拉齐，二级目录直接渲染。文件夹列表来自配置（见〈决策·folder-list〉）。
- **`GET /api/conversation?agentId&cwd`** —— 取某会话完整历史。内部：`Agent.listRuns` → 逐 run `run.conversation()`（先 `run.supports("conversation")` 守卫，不支持则降级 `messages.list`，见〈未决·conversation-support〉）。为什么按 run 聚合：一个会话由多次 run 组成，历史即各 run 的 `ConversationTurn` 顺序拼接。
- **`POST /api/chat`** —— body 含 `cwd`、可选 `agentId`（无则新建会话）、`text`。**响应是 chunked NDJSON 流**：每收到一个 `run.stream()` 的 `SDKMessage` 就写一行 JSON，末尾写一行显式 `done`（带终态 status）。为什么 send+stream 合一：单用户场景下"发一句、收一流"是同一个逻辑单元，合一免去 SSE 那样"另开通道 + 按 runId 关联"的复杂度（见〈决策·transport〉）。

### 3.3 关键实现约定（压测逼出，必须落地）
每条约定就地写明理由：

1. **NDJSON 以显式 `done` 行结尾（带 `finished/error/cancelled`）**——否则前端无法区分"正常结束"与"连接断开"，只能靠超时猜。
2. **浏览器断连时 run 继续跑完并持久化、不 cancel**——run 在后端进程内，写流 EPIPE 只停止推送；用户重开该会话可从 `conversation()` 读到完整结果。这是"单用户、结果不丢"的最简选择。
3. **同会话流未结束禁止再发**（前端禁用输入）——本地不报 agent_busy，串行化避免两个 run 抢同一 agent；后端兜底可用 `local.force`。
4. **工具调用防御式渲染**——`tool_call` 的 `args`/`result` 是 `unknown` 且 schema 不稳定，前端当作未知值折叠展示 `JSON.stringify`（旧 viewer 已验证可行）。

### 3.4 非直觉 API 用法（已验证，供实现参考）
后端把活 run 事件转 NDJSON 的核心循环（`[已验证: @cursor/sdk@1.0.23 run.d.ts / messages.d.ts]`）：

```typescript
// 伪代码：仅示意事件→NDJSON 的转发结构，字段以 .d.ts 为准
const run = await agent.send(text);
for await (const event of run.stream()) {   // event: SDKMessage，含 type 判别字段
  res.write(JSON.stringify(event) + "\n");   // 逐行 NDJSON
}
res.write(JSON.stringify({ type: "done", status: run.status }) + "\n");
res.end();
```

历史重建（`[已验证: conversation-types.d.ts 的 ConversationStep 判别联合]`）：`listRuns` → 每个 run `conversation()` → 展开 `turn.steps`，按 `assistantMessage / toolCall / thinkingMessage` 分别渲染。

## 4. 实施计划

### 4.1 子任务拆解
| # | 任务 | 涉及模块 | 验收标准 | 优先级 |
|---|------|----------|----------|--------|
| 1 | 初始化 Node/TS 工程 | `package.json`、ts 配置 | `@cursor/sdk` 装好，Node 服务能起 | 必须 |
| 2 | SDK 交互层 + 句柄缓存 | server/agent 模块 | 能 create/resume/send/stream/list/listRuns，按〈决策·agent-cache〉 | 必须 |
| 3 | `GET /api/folders` | server | 返回预定义文件夹及各自会话列表 | 必须 |
| 4 | `GET /api/conversation` | server | 返回富历史，按〈决策·history-source〉，含〈未决·conversation-support〉守卫 | 必须 |
| 5 | `POST /api/chat`（NDJSON 流） | server | 流式返回事件、以 `done` 收尾，按 §3.3 约定 1/2/3 | 必须 |
| 6 | 前端单页：侧边栏 + 二级会话 | 单页 | 展示文件夹→会话，点击/新建进主对话页 | 必须 |
| 7 | 前端：主对话页历史渲染 | 单页 | 渲染 user/assistant/thinking/工具（§3.3 约定 4） | 必须 |
| 8 | 前端：发送 + NDJSON 流式增量 | 单页 | fetch+ReadableStream 逐行渲染，流中禁用输入 | 必须 |

### 4.2 测试要点
- [ ] 新建会话 → 发一句 → 事件流式出现 → `done` 收尾。
- [ ] 已有会话追问，上下文保留（引用上一轮内容）。
- [ ] 打开历史长会话，thinking 与工具调用正确渲染。
- [ ] 边界：流中途关页面，后端不崩、会话结果仍可从历史读到。
- [ ] 边界：`run.supports("conversation")` 为假时走降级路径不报错。

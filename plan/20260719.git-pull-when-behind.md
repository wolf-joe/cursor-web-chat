# Diff Overlay：落后远程时拉取（ff-only）

> **文档定位**：**活 spec**（会随实施反复更新）。
> 「关键决策与未决项」表是唯一真相源；正文引用它、不复述它。
> 本需求叠在 `plan/20260718.git-commit-push.md` 之上：补「事前拦住落后 + 显式快进拉取」，不重做一锤子 commit+push。

## 0. 一页纸（骨架先行）

- **一句话**：打开/刷新 Diff Overlay 时 `fetch` 并算出与上游的 ahead/behind；若落后则置灰「提交并推送」、提供「拉取」（仅快进）；拉取成功后再允许提交推送，避免先本地 commit 再被非快进 push 拒绝。
- **承重决策**：
  1. **sync 并入 git-diff** —— 打开/刷新才 fetch，不进标题栏 status，因为开销要可控且与「status 轻 / diff 重」分层一致（详见 〈决策·sync-in-diff〉）。
  2. **仅 `pull --ff-only`** —— 独立 POST；禁止 merge/rebase/force，因为动机是消掉「触发 merge / 搅分支」，不是做完整 git 客户端（详见 〈决策·ff-only-pull〉）。
  3. **UI + 后端双闸门** —— Overlay 置灰提交；`commit-push` 执行前再拒 behind/`fetch_failed`，因为只靠 UI 仍可被直打 API 先落 commit（详见 〈决策·commit-behind-guard〉）。
  4. **分叉用文案、拉取仍可点** —— ff-only 解不了分叉，点了失败提示即可，不假装能修好（详见 〈决策·diverge-copy-keep-pull〉）。
  5. **fetch 失败保守禁用提交** —— 不知道是否落后时不许推，避免假「已同步」（详见 〈决策·fetch-fail-block〉）。
- **验收总目标**：落后时可拉不可推；对齐（或仅 ahead）且 dirty 时可走原 commit+push；分叉/冲突/fetch 失败均有明确提示且不静默改历史；标题栏 status 不 fetch；标题栏常驻 `git` 入口（干净也可开 Overlay）；SSE 不断。

## 1. 需求背景

### 1.1 原始需求

> 仓库若未与远程同步、远程有更新，再 commit and push 会造成分支干扰或触发 merge。希望：当前比远程落后时，在 commit push 旁加「拉取」按钮，并置灰 commit and push；拉取冲突则接口报错提示。评估可行性与开销后出方案。

后续确认：fetch 用方案 A（仅 Overlay 打开/刷新）；pull 仅快进；dirty 允许尝试 pull、失败前端提示；分叉单独文案且保留拉取按钮；fetch 失败保守禁用提交；成功后重拉并可提交；实现选「diff 内嵌 sync + 独立 pull + 后端闸门」；**单独成文**（不整篇改写 commit-push 方案）。

### 1.2 背景与动机

`plan/20260718.git-commit-push.md` 刻意不做 pull：落后时往往变成 **commit✓ push✗**，本地已多出一个 commit，处理成本高于「先拉齐再提交」。本需求把同步检查前置到 Overlay，并给出唯一安全写动作：快进拉取。

### 1.3 目标与验收标准

- Overlay 打开/刷新后能区分：对齐 / 仅 ahead / 仅落后 / 分叉 / 无上游 / `fetch_failed`（〈决策·sync-states〉）。
- 仅落后：提交置灰，显示拉取；ff 成功后若仍 dirty，提交可用（〈决策·behind-ui〉）。
- 分叉：单独文案；拉取可点，失败有错误（〈决策·diverge-copy-keep-pull〉）。
- fetch 失败：提交不可用并提示（〈决策·fetch-fail-block〉）。
- 直调 `commit-push` 在 behind / `fetch_failed` 时不落 commit（〈决策·commit-behind-guard〉）。
- pull 冲突/非快进/脏文件将被覆盖：接口报错，工作区不被半拉成功误导（〈决策·ff-only-pull〉）。

### 1.4 约束与前提

- 仍只服务 `config.json` 白名单 cwd；不接受客户端任意 git args（继承 commit-push）。
- 不做 merge / rebase / force / reset / stash UI（〈决策·ff-only-pull〉〈决策·no-dangerous-git-extend〉）。
- 标题栏 `/api/git-status` 保持轻量、不 fetch（〈决策·sync-in-diff〉）；常驻 `git` 按钮，dirty 仅改数字与颜色（〈决策·title-git-always〉）。
- 打开 Overlay / 拉取 / 提交过程不得 `detachStream`（继承 〈决策·keep-stream〉）。
- 易变字段名、超时、错误摘要上限收口 §5，正文不复述多份。

## 2. 现状分析

### 2.1 相关代码/系统现状

- **轻量 status**：`src/gitStatus.ts` + `GET /api/git-status`——仅 porcelain + 分支；事件驱动刷新，无轮询、无 fetch。标题栏常驻 `git` 按钮（〈决策·title-git-always〉）。
- **Diff Overlay**：`getGitDiff` / `GET /api/git-diff`；前端 `loadDiff` 在打开与点刷新时调用；顶栏已有「提交并推送」。
- **写路径**：`src/gitCommit.ts`——`add -A → commit → push`；cwd 内存 busy 锁；无 pull；无 behind 检查。
- **旧决策**：commit-push 的 `write-path-scope` 写明不做 pull——由本需求局部放开 ff-only，并在旧文档决策表回指（〈决策·write-path-pull-exception〉）。

### 2.3 现状与目标的差距

| 目标 | 现状 | Gap |
|------|------|-----|
| 知道是否落后 | 无 fetch / ahead-behind | diff 响应带 sync |
| 落后时不可提交、可拉取 | 有 dirty 即可点提交 | UI 状态机 + pull API |
| 防「先 commit 再被拒」 | 仅靠 push 失败 | 后端 commit 闸门 |
| 分叉可理解 | 无 | 文案 + ff-only 失败回传 |

### 2.4 影响范围

- **会改**：`src/gitDiff.ts`（内嵌 fetch+sync）、新建 pull 能力（独立模块或并入 git 写模块）、`src/gitCommit.ts`（闸门 + 共用锁）、`src/server.ts`、`public/gitDiff.js` / `index.html` / `dom.js` / `api.js` / `style.css`；本文件；旧 commit-push 决策表一行回指。
- **基本不动**：`git-status` 语义、agent / runHub / SSE、llm-proxy / commit message。

## 3. 方案设计

### 方案 A：diff 内嵌 sync + POST pull + 后端闸门（选定）

- **思路**：`GET /api/git-diff` 在返回 files 同时完成 fetch 与 ahead/behind；顶栏按 sync 控制「提交并推送」与「拉取」；`POST /api/git-pull` 只跑 `git pull --ff-only`；`commit-and-push` 加锁后、add 前再确认未落后且 sync 可用。
- **改动范围**：见 §2.4。
- **优点**：一次加载拿齐 Overlay 所需；UI/API 双保险；锁模型沿用现成 busy。
- **缺点**：diff 接口带 fetch 副作用（只更新 remote-tracking）；打开略慢。
- **工作量**：M

### 未选

- **B**：仅 UI 置灰、后端不闸门——仍可直打 API 先落 commit。
- **C**：用 GET 带 pull 副作用——写操作挂在 GET，与现有风格冲突。

### 执行步骤

原则：**可失败的网络 fetch 与状态展示前置；ff-only pull 与 commit 均为写路径且互斥；commit 闸门在 add 之前。**

1. **扩展 `getGitDiff`** —— 仓库内先 `git fetch`（失败则 `fetch_failed` + 错误摘要，仍尽量返回本地 files）；成功则对 `HEAD...@{upstream}` 计数；无上游单独状态。字段按 〈决策·sync-states〉〈决策·sync-response-shape〉。
2. **`POST /api/git-pull`** —— 白名单 cwd；`git pull --ff-only`；与 commit **共用** busy 锁（〈决策·shared-busy-lock〉）；业务失败 200+`ok:false` + 错误摘要；忙 409。
3. **`commitAndPush` 闸门** —— 进入写序列后、`add` 前按 〈决策·commit-behind-guard〉〈决策·guard-refetch〉再 fetch 并拒绝 behind / fetch_failed / 无上游（无上游本就会 push 失败，闸门文案可更早明示）。
4. **Overlay UI** —— 顶栏「拉取」；`updateCommitButton` / 拉取可见性按 〈决策·behind-ui〉〈决策·diverge-copy-keep-pull〉〈决策·fetch-fail-block〉；拉取中锁按钮；成功后 `loadDiff` + `refreshGitDirty`；过程不 `detachStream`。
5. **文档回指** —— 旧 plan `write-path-scope` 旁注本需求例外（〈决策·write-path-pull-exception〉）。
6. **typecheck** —— `npm run typecheck`。

### 压力测试（残余风险）

| 压力维度 | 具体场景 | 方案表现 | 是否需要防御性设计 |
|----------|---------|----------|------------------|
| 竞态 | 打开后远程又推新提交 | UI 曾显示可提交 | 是：commit 前再判 behind（〈决策·commit-behind-guard〉） |
| 故障 | fetch 超时 | 不知是否落后 | 是：`fetch_failed` + 禁用提交（〈决策·fetch-fail-block〉） |
| 故障 | 落后 + 重叠脏文件 pull | 应失败且不改 HEAD | 是：ff-only + stderr 回传（已验证 would be overwritten） |
| 并发 | pull∥commit 同 cwd | 双写风险 | 是：共用 busy 锁 |
| 规模 | 大仓库 fetch 慢 | Overlay 变慢 | 是：仅 Overlay 触发；超时上限 〈决策·fetch-timeout〉；banner「同步远程中」 |
| 操作 | fetch 更新 remote-tracking | 非工作区改动 | 可接受；文档写明副作用 |

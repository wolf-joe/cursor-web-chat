# 取消轮次：展示与模型上下文对齐

> **文档定位**：**活 spec**（会随实施反复更新）。
> 「关键决策与未决项」表是唯一真相源；正文引用它、不复述它。

## 0. 一页纸（骨架先行）

- **一句话**：停止/取消不回滚 checkpoint；前端却把 cancelled 整轮藏掉，造成「UI 以为没发生、模型仍记得」。本需求只修**展示与上下文一致**，不改取消语义、不自动遗忘。
- **承重决策**：
  1. **以 checkpoint 是否推进为展示闸门** —— 未推进的取消轮不进模型上下文，也不进 UI；已推进的必须展示（详见 〈决策·checkpoint-advanced-gate〉）。
  2. **半截输出走 `conversation()`** —— cancelled 上已验证可用（详见 〈决策·cancelled-conversation〉）。
  3. **用户原文优先 `messages.list` 按「已推进」轮配对，blob 差分作备选** —— 已推进取消轮的 user 会出现在 `messages.list`；配不上再 `store.checkpoints.get`（详见 〈决策·user-text-from-blobs〉 / 〈决策·blob-user-text-codec〉）。
  4. **`messages.list` 配对服务全部已推进轮** —— 含已推进 cancelled；未推进取消仍剔除（详见 〈决策·finished-backfill-untouched〉）。
  5. **真正忘掉仍靠「撤销上一轮」** —— 本方案不把停止改成 undo（详见 〈决策·forget-via-undo〉）。
- **验收总目标**：Pranks→Proxy 类会话重开后能看到已推进的取消轮（用户原文 + 半截步骤 + 已取消标）；早停未推进的取消轮不出现；其后 finished 轮用户气泡不错位；停止本身不清除模型记忆，文案引导需要时用撤销。

## 1. 需求背景

### 1.1 原始需求

> 说错字后点停止/取消，等网页上看不到那轮后改口重发；AI 思考里仍回应错别字。展示与模型上下文不一致，需分析并出方案。

后续确认：案发为 skills 工作区「清理 qBittorrent…」会话 Turn1 `Pranks`→Turn2 `Proxy`；动作为停止而非撤销；选定方案 B（展示诚实化）；并收窄为——**仅展示 checkpoint 已推进的取消轮**；用户原文读 SDK SQLite（`messages.list` / blob）；send 时自存 fallback **未实现**。

### 1.2 背景与动机

取消只 `run.cancel()`；undo 才拨 checkpoint + 删 run + 清缓存。`history.ts` 的 `决策·cancelled-turn-drop` 整轮丢弃非 finished，重开后 UI 干净，但已推进的 `latestCheckpoint` 仍含该轮用户话与半截工具/思考，续聊模型看得见。

### 1.3 目标与验收标准

- 重开/刷新：checkpoint 已推进的 cancelled（及同类 error，若同样推进）可见，并标状态 +「AI 续聊可能仍记得；忘掉请用撤销」（〈决策·honest-cancelled-ui〉）。
- 未推进的取消轮：历史中不出现（〈决策·checkpoint-advanced-gate〉）。
- finished 轮用户气泡不错位（〈决策·finished-backfill-untouched〉）。
- 取消 → 撤销 → 再发：模型不再带取消轮（沿用现有 undo，〈决策·forget-via-undo〉）。

### 1.4 约束与前提

- 不改 `run.cancel()` 的 SDK 语义；不做方案 A（取消后自动丢弃）。
- 不解析/依赖未导出的私有 SDK 模块路径作为长期契约；读盘优先走已公开的 `SqliteLocalAgentStore.checkpoints.get` / `runs` 上的 checkpoint ref（〈决策·user-text-from-blobs〉）。
- blob 内对话结构属 SDK 内部编码，解析细节以实施时对照真实 blob 为准，收口 §5（〈未决·blob-user-text-codec〉）。

## 2. 现状分析

### 2.1 相关代码/系统现状

- **取消**：`cancelRun` → `run.cancel()` → hub `done cancelled` → `clearBusy`（句柄仍在缓存）；不拨 checkpoint。
- **历史**：`getConversationHistory` 跳过非 `finished`；finished 用 `conversation()` + `messages.list` 按位补 user。
- **撤销**：拨 `latestCheckpoint` ← 末轮 `startCheckpointRef`，删 run/events，`evict` 缓存。
- **实测（案发 agent）**：Turn1 cancelled：`start=null`、`latest=e25acc98…`（推进）；blob 树含完整「Pranks」用户句；Turn2 思考开场承认 Pranks→Proxy。Turn6 cancelled：`start==latest`（未推进），不进模型上下文。

### 2.2 问题定位

- **类型**：展示与真实上下文语义缺口（非单纯前端过滤写错）。
- **根因**：停止 ≠ 遗忘；UI 按 status 隐藏，模型按 checkpoint 续聊；旧注释「cancelled 永不推进 checkpoint」不完整。

### 2.3 现状与目标的差距

| 目标 | 现状 | Gap |
|------|------|-----|
| UI 与「模型是否记得」同判据 | 按 status 一刀切 | 按 checkpoint 是否推进 |
| 已推进取消轮可见 | 整轮丢弃 | 纳入 history + 标状态 |
| 用户气泡 | `conversation()` 无 user；`messages.list` 无 cancelled user | 从 checkpoint blob 捞 |
| 用户知如何忘掉 | 易误以为停止即忘 | 文案指向撤销 |

### 2.4 影响范围

- **会改**：`src/history.ts`（闸门 + 组装）；新建/内嵌「从 checkpoint 取本轮 user 文本」；`public/render.js` / `stream.js` / 样式与短文案；本文件；必要时澄清 `决策·cancelled-turn-drop` 旁注。
- **基本不动**：`cancelRun`、undo 落盘逻辑、runHub 消费循环、agent 主协议。

## 3. 方案设计

### 选定：展示诚实化 + checkpoint 闸门 + blob 捞用户原文（方案 B 收窄版）

- **思路**：历史里对 cancelled/error：若 `startCheckpointRef.rootBlobId !== latestCheckpointRef.rootBlobId`（null≠有值算推进）则保留；`conversation()` 填半截 steps；用户原文从该 run 的 latest 相对 start 的 checkpoint blob 差分/解析得到；UI 标「已取消/出错」并提示撤销。
- **改动范围**：见 §2.4。
- **优点**：与模型记忆判据一致；早停不噪音；不碰取消语义。
- **缺点**：blob 解析有 SDK 升级风险；停止后直接改口仍可能「记得」（需撤销）——产品上接受。
- **工作量**：M

### 未选（摘要）

- **A 取消后自动丢弃**：能直接修「改口仍记得」，但改变停止语义；本次明确选 B。
- **仅文案/双按钮**：不修重开后不一致。
- **send 时自存用户原文作备选**：〈未决·persist-user-text-fallback〉——**未实现**；本次展示只读 SDK SQLite（`messages.list` / checkpoint blob）。

### 执行步骤

原则：先闸门与展示骨架，再抠用户原文；finished 配对全程不动。

1. **闸门 + 纳入 history** —— 非 finished 且未推进则 `continue`；已推进则 `conversation()` + 带 `status`（为何：先对齐「该不该出现」）。
2. **用户原文从 blob** —— `store.checkpoints.get` 读 start/latest 树，抽出本轮 user 文本填回 `userMessage`（为何：API 展示层不给 cancelled user；盘上有）（〈未决·blob-user-text-codec〉实施时坐实）。
3. **前端诚实 UI** —— 状态条/样式 + 撤销引导；cancelled 终态后允许 refetch 与重开一致（〈决策·honest-cancelled-ui〉）。
4. **回归** —— finished backfill；早停取消不可见；Pranks 类重开可见。

### 压力测试（残余风险）

| 压力维度 | 场景 | 方案表现 | 是否需防御 |
|----------|------|----------|------------|
| 外部契约 | blob 编码变更导致捞不到 user | 仍展示 steps + 已取消，用户气泡缺或占位 | 是：降级占位，不拖垮整页；自存 fallback 未实现 |
| 操作 | 停完不撤销直接改口 | 模型仍可能记得 | 是：文案写清；不静默当已忘 |
| 回归 | 误把 cancelled 计入 messages 按位配对 | 错位 | 是：〈决策·finished-backfill-untouched〉 |

## 5. 关键决策与未决项（唯一真相源）

### 5.1 已定决策 / 约束

| 名字 | 结论 | 来源 | 影响位置 |
|------|------|------|----------|
| checkpoint-advanced-gate | 仅当 run 的 start/latest checkpoint root 不同（含 start 空、latest 有）时展示非 finished 轮 | 用户收窄 + 案发 SQLite / store.runs 实测 | §0、§3、任务1 |
| cancelled-conversation | cancelled 且已推进时 `run.conversation()` 返回半截 steps；早停可为 `[]` | 对本仓库案发 run 的 SDK 实测 ✅ | §0、任务1 |
| user-text-from-blobs | 用户原文：先对「已推进」轮用 `messages.list` 按位补；配不上再 `checkpoints.get` + blob 差分解析；不靠未导出私有 proto | 案发实测：已推进取消的 user **在** messages.list；blob 树亦有 JSON user 叶子 ✅ | §0、任务2、〈决策·blob-user-text-codec〉 |
| finished-backfill-untouched | `messages.list` 按位配对服务「checkpoint 已推进」的轮次（含已推进 cancelled/error，不只 finished）；未推进取消仍剔除。实施时坐实：已推进取消的 user **会**出现在 `messages.list`，若只配 finished 会错位 | 既有错位教训 + 案发 Pranks 轮实测修正 | §0、任务1 |
| forget-via-undo | 停止不遗忘；忘掉用撤销（拨 checkpoint） | 用户选 B；既有 undo | §0、文案 |
| honest-cancelled-ui | 已展示的非 finished 轮必须标状态并提示可能仍被模型记得；cancelled/error 终态后 refetch 与重开一致 | 用户选 B | 任务3 |
| blob-user-text-codec | 根 blob merkle（32 字节子 id）；本轮新增叶子含 JSON `role:user` + `<user_query>` 文本；`messages.list` 未配上时再走 blob；失败则占位 | 案发 blob 树实测 ✅ | 任务2 |

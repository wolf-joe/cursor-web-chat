# 每轮展示上下文窗口占用（used / max）

> **文档定位**：**活 spec**（会随实施反复更新）。  
> 取数实证见 `docs/checkpoint-context-usage.md`；本文件只定产品接入与实施边界。

## 0. 一页纸（骨架先行）

- **一句话**：从每轮 run 结束时的 checkpoint root blob 读出 `used_tokens` / `max_tokens`，挂到该轮 meta；公开 `Run.usage` 仍是计费合计，两套数并存、不混用。
- **承重决策**：
  1. **方案 C 取数** —— 读该 run 的 `latestCheckpointRef.rootBlobId`，只解析 `ConversationStateStructure` field 5；不挂 Connect interceptor、不打 SDK patch（详见〈决策·source-checkpoint〉）。
  2. **按 run 读、不按 agent** —— 历史每一轮用自己的 end checkpoint；`agent.latestCheckpoint` 只代表末态，不能回填旧轮（详见〈决策·per-run-checkpoint〉）。
  3. **checkpoint 即持久化** —— 不做 sidecar；history / done 都现场读 blob，无数据则隐藏（详见〈决策·no-sidecar〉）。
  4. **挂点沿用 run meta** —— 与 model / `totalTokens` 同级，写在该轮最后一条 assistant 底部；文案为 `used / max`（详见〈决策·meta-copy〉）。
  5. **解析失败降级** —— 与 blob 用户原文同套路：失败返回 null，不拖垮整页历史（详见〈决策·parse-degrade〉）。
- **验收总目标**：有 checkpoint 且含 field 5 的轮次，直播结束与刷新/重开后都能看到同一套 used/max；无数据的轮次不显示该段；不引入 SDK patch。

## 1. 需求背景

### 1.1 原始需求
> Cursor SDK 没有返回当前 AI 模型的上下文使用情况，只返回了每个 turn 消耗的 token 总量。希望在前端每个 turn 展示完之后，额外展示当前模型的上下文使用情况（used / max）。本轮结束后展示；刷新或重开历史轮次也要能看到；拿不到数据时隐藏。

### 1.2 背景与动机
公开 `TokenUsage` 是计费累加，可远超上下文窗口，不能当「窗口占用」进度。Checkpoint 里已有 `ConversationTokenDetails`，只需接到现有 run meta UI。

### 1.3 目标与验收标准
- 展示 **used** 与 **max**（上下文窗口口径）。
- **本轮结束后**可见；**刷新 / 重开历史**仍可见且与直播一致（同源：该 run 的 end checkpoint）。
- 无 `latestCheckpointRef`、无 field 5、或解析失败 → **不渲染**该段。
- 不把 `run.usage.totalTokens` 当成窗口占用。

### 1.4 约束与前提
- 只动展示与 checkpoint 只读解析；不改 agent 主循环协议（详见〈决策·source-checkpoint〉）。
- cwd 仍须落在 `config.json` folders；读 store 走现有 `getLocalStore`（详见〈决策·store-reuse〉）。
- Proto field 号属未公开契约，升级后用探针回归（详见〈未决·proto-drift〉仅作监控项，不挡首版）。

## 2. 现状分析

### 2.1 相关代码/系统现状
- **直播**：`runHub` 在 stream 结束后广播 `done{ model, usage }` → 前端 `appendRunMeta` 画 model · totalTokens → 再 refetch `/api/conversation` 整段重绘。
- **历史**：`history.getConversationHistory` 把 `run.model` / `run.usage` 挂到 `RunTurns`；前端同样 `appendRunMeta`。
- **Checkpoint 读取先例**：`checkpointUserText.ts` 已用 `store.checkpoints.get` + 手写 protobuf 游标；**禁止**为占比去 BFS 整棵 merkle（慢且易误伤）。
- **实证**：`docs/checkpoint-context-usage.md` —— 有 checkpoint 的 run 上 field 5 命中率本机样本为 1.0；`scripts/probe-checkpoint-token-details.ts` 可回归。

### 2.3 现状与目标的差距
| 目标 | 现状 | Gap |
|------|------|-----|
| used/max | 只有计费 `TokenUsage` | 从 root field 5 解析并挂到 API/UI |
| 历史回看 | refetch 只带 `run.usage` | history / done 都附带 context 字段 |
| 无则隐 | — | null 时不渲染 |

### 2.4 影响范围
- `src/`：新建 checkpoint → context 解析模块；`history.ts`；`runHub.ts`（done 载荷）。
- `public/render.js`（及 stream 的 done 路径共用的 `appendRunMeta`）。
- 不改：SDK patch、Connect interceptor、TTS/undo 清理逻辑（无 sidecar 可清）。

## 3. 方案设计

### 最终选定：方案 C（checkpoint field 5）

- **思路**：每个展示中的 run，用其 `latestCheckpointRef.rootBlobId` 取 root bytes，解析 `token_details` 的 used/max，随 history 与 done 下发；UI 有值才画。
- **改动范围**：解析模块 + history/runHub 字段 + `appendRunMeta`。
- **优点**：已实证；无 patch；checkpoint 自带历史；与现有 blob 读法一致。
- **缺点/风险**：依赖未公开 field 号（升级用探针盯）；done 瞬间若 checkpoint 尚未写上最终 details，可能暂缺——依赖随后 refetch（详见压力表）。
- **工作量**：S。

### 未采纳（摘要）
- **Connect interceptor（B）**：对只要 used/max 非必需。
- **Sidecar 按 runId 落盘**：方案 C 下 checkpoint 已是持久化源；首版不做，避免与 undo/delete 再对一套生命周期。

### 执行步骤

原则：**取数只读、展示可缺省；先 history 同源，再补 done 即时性。**

1. **抽出解析函数** —— 从 probe 收成 `src/` 模块（建议与 `checkpointUserText.ts` 并列）：输入 root `Uint8Array`，只扫顶层 field 5 → 嵌套 field 1/2 → `{ usedTokens, maxTokens } | null`。理由：产品路径禁止整树扫描；与实证文档 §3.3 一致。
2. **history 组装时附带** —— 对每个进入展示列表的 run，若有 `latestCheckpointRef.rootBlobId`，`checkpoints.get` + 解析，写入 `RunTurns`（字段名见〈决策·api-shape〉）。理由：刷新/重开只走这条，是正确性主路径。
3. **done 事件附带** —— stream 终态后用该 live run 的 checkpoint ref 再读一次，写入 `done`。理由：refetch 前用户也能立刻看到；读失败则省略字段。
4. **前端 `appendRunMeta`** —— 在现有 model · tokens 旁，若 used/max 皆为有效数字则追加一段（〈决策·meta-copy〉）；缺一则整段不画。理由：无新 Overlay，符合「额外一块区域」的轻量形态。
5. **探针保留** —— `scripts/probe-checkpoint-token-details.ts` 继续只读回归；实施后若脚本仍含整树启发式，收紧为「只解析 root field 5」与产品代码一致。

### 压力测试（残余风险）

| 压力维度 | 具体场景 | 方案表现 | 是否需要防御性设计 |
|----------|---------|----------|------------------|
| 故障容错 | blob 缺失 / 解析失败 / 无 field 5 | 返回 null，UI 隐藏 | 是——〈决策·parse-degrade〉，catch 不抛到 HTTP |
| 时序 | done 早于最终 token_details 写入 | 该次 done 可能无字段；refetch 再读 | 是——接受短暂缺失；不以计费 usage 兜底冒充 |
| 规模 | 会话上百 run | 每 run 一次 get + 浅解析 | 是——禁止 BFS；若日后变慢再议缓存（非首版） |
| 演进 | SDK 改 field 布局 | 全员隐藏直至修好解析 | 是——探针回归；见〈未决·proto-drift〉 |
| 外部契约 | `checkpoints.get` / field 号 | 公开 store API ✅；field 号靠实证 | 是——field 契约记入决策表，不依赖私有 proto 包 |

## 4. 实施计划

### 4.1 子任务拆解

| # | 任务 | 涉及文件/模块 | 验收标准 | 优先级 |
|---|------|---------------|----------|--------|
| 1 | root field 5 → used/max 解析 | 新建 `src/checkpointContextUsage.ts`（名可微调） | 对探针样本与手动挑的 root blob 得到与文档一致的 used/max；畸形输入返回 null | 必须 |
| 2 | history 附带字段 | `src/history.ts` | `/api/conversation` 里有 checkpoint 的 run 带上字段；无则缺省 | 必须 |
| 3 | done 附带字段 | `src/runHub.ts` | 终态 SSE `done` 可选带同名字段 | 必须 |
| 4 | UI 渲染 | `public/render.js`（`appendRunMeta`） | 有值显示；无值与现网一致；与 totalTokens 并存不混淆 | 必须 |
| 5 | 收紧探针 | `scripts/probe-checkpoint-token-details.ts` | 只测 root field 5；文档命令仍可用 | 应该 |

### 4.2 测试要点
- [ ] 选一 finished 长会话：直播结束后 meta 有 used/max；硬刷新后同轮数字一致。
- [ ] 对照 `run.usage.totalTokens`：可远大于 max，UI 仍显示 checkpoint 的 used/max。
- [ ] 无 checkpoint / 早停未推进轮：不出现 used/max 段。
- [ ] 解析抛错或坏 blob：历史接口仍 200，该轮无 context 段。
- [ ] `npx tsx scripts/probe-checkpoint-token-details.ts <cwd>` 命中率与「有 checkpoint 的 run」同量级。

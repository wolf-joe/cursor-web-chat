## 0. 一页纸（骨架先行）

- **一句话**：企微侧输出分两轨——过程走**一条**原地刷新的 stream 气泡（只追加、内容极简），正文在 run 结束时作为 markdown 终稿一次性送达（必要时按字节分片）。
- **承重决策**：
  1. **过程 stream、正文 markdown** —— 过程需要的是「一条会变的气泡」，正文需要的是「瞬间出现且不受 10 分钟窗约束」。两者诉求相反，共用一条载体必然一头受损（详见 〈决策·stream-progress-markdown-final〉）。
  2. **进度内容只追加、每步一行** —— 企微对 stream 是固定速率逐字动画，延迟只跟推进去的字符量成正比；thinking 正文一律不发、工具只留「名字 + 关键目标」，一步一行（详见 〈决策·thinking-one-line〉/〈决策·tool-line-compact〉/〈决策·progress-append-only〉）。
  3. **滚动气泡而不是硬截止** —— stream 自首帧起 10 分钟必须 finish，是 msgtype 自身的属性；同 req_id 可连发已实测，所以到点（或行数过多）就 finish 当前气泡、开一个新 stream.id 接着刷。长任务因此既不断档也不刷屏（详见 〈决策·stream-rollover〉）。
  4. **正文不截断，只分片** —— 20480 字节是服务端硬上限且**超限整条拒收**（`errcode 40058`），不是截断。分片一律按字节算（详见 〈决策·final-chunk〉）。
  5. **频控有显式账本** —— stream 的每次刷新都计 1 条，与终稿分片共用每会话 30 条/分钟、1000 条/小时。进度帧可丢、终稿不可丢（详见 〈决策·digest-budget〉）。
- **验收总目标**：过程只占一条气泡（超 9 分钟或超长时才滚动出新的一条）；正文瞬间出现、不再落后网页；超 20480 字节正文分多条且代码块不被切坏；cancelled/error 有明确终态；单轮 respond 次数有账本、不触发频控；40 分钟轮次的正文仍能送达。

## 1. 需求背景

### 1.1 原始需求

> wecom bridge 不太行，所有内容全挤在一个卡片里，特别长轮次的场景会触发企业微信的长度限制。另外所有内容是通过流式传输的，在企业微信上有打字机的效果，但是打字机效果很慢，导致网页都出来内容了，企业微信还在慢吞吞的打印之前的内容。

追加需求（同日实跑后）：

> 我还是希望中间结果（工具调用/thinking）放在 stream 里，最后一个 AI 的回复发 markdown 卡片。中间结果（每 3s 一次卡片）的卡片太多，太打扰了。

以及：thinking 只需要一行提示，不要正文。

### 1.2 背景与动机

手机上看一个长轮次时，原实现是「网页早已出完，企微还在逐字打印几分钟前的内容」，超过 9 分钟的轮次结果直接送不到。过程可见性要保留，但它既不该拖慢正文，也不该刷屏。

### 1.3 目标与验收标准

- [ ] 正文送达不再有动画滞后（markdown 无逐字动画已实测，详见 〈决策·markdown-no-typewriter〉）。
- [ ] 过程默认只占**一条**气泡，原地刷新（详见 〈决策·stream-progress-markdown-final〉）。
- [ ] 超过 10 分钟、乃至 40 分钟的轮次，正文仍能送达；进度气泡靠滚动续窗，不再出现「强制结束」后再无下文（详见 〈决策·stream-rollover〉）。
- [ ] 进度里 thinking 只占一行、不含正文（详见 〈决策·thinking-one-line〉）。
- [ ] 长正文按 20480 字节分片，不再自截断（详见 〈决策·final-chunk〉）。
- [ ] cancelled / error 结束时有明确终态，不静默。
- [ ] 主服务 chat / stream / cancel 协议与 runHub 语义零改动。

### 1.4 约束与前提

- 桥接仍是独立进程、仍只经 HTTP 调主服务（沿用 MVP 的 `决策·http-drive`、`决策·separate-process`）。
- 输出通道只有一条：回调带来的 `req_id`。主动推送（`aibot_send_msg`）已判死（详见 〈决策·send-msg-dead〉）。
- 指令语义（`help`/`new`/`stop`）、binding 落盘、cwd 白名单、msgid 去重不动。
- 企微频控与消息上限是硬边界（详见 〈外部契约·rate-limit〉/〈外部契约·markdown-limit〉）。
- **同一个 bot 只允许一条长连接**：本机 Supervisor 的 `cursor-wecom` 与任何手工桥接/验证脚本互斥，跑脚本前先 `supervisorctl stop cursor-wecom`。
- `WECOM_BASE_URL` 必须与主服务 `PORT` 一致（默认 3000）；本机 Supervisor 曾漏配导致 `ECONNREFUSED`，模板已补进 `deploy/supervisor.ini`。

## 2. 现状分析

### 2.1 相关代码/系统现状

当前（初版实施后的状态）：`bridge.ts` 收到文本 → `POST /api/chat` → 订阅 SSE；`DigestBuffer` 按 3 秒窗口把活动渲染成一条 markdown 气泡下发，`ReplyAccumulator` + `chunkMarkdown` 在 run 结束时发终稿；`ReplyChannel` 管频控账本、两级优先级与断线重试。`ws.ts` 只有 `respondMarkdown`，`respondStream` 已删。

改造前的原始状态（供理解为什么会走到这一步）：一条 stream 气泡承载 thinking 全文 + 工具 args + 正文，2 秒节流全量替换，9 分钟强制 finish，断线即放弃本轮。

### 2.2 问题定位

- **根因（打字机慢）**：企微客户端对 stream 做固定速率逐字动画，延迟只与推进去的字符量成正比，调节推送间隔无效。原实现往动画气泡里塞了约 4 倍冗余（thinking 全文 + args + 正文）。
- **根因（离散卡片吵）**：3 秒一条 markdown 卡片时，一个 10 分钟轮次会留下约 200 条气泡。markdown 不能原地刷新，这是它换来「无动画」的代价——用在正文上是净收益，用在高频进度上是灾难。
- **「触发长度限制」的真实归因**：企微侧无 errcode，是本仓 18000 字节自截断与 9 分钟 footer 写进内容里的提示。`stream.content` 的真实上限至今未被触碰（详见 〈未决·stream-content-limit〉）。

### 2.3 现状与目标的差距

| 现状（初版实施后） | 目标 |
|------|------|
| 进度每 3 秒一条独立 markdown 卡片，刷屏 | 进度回到一条原地刷新的 stream 气泡 |
| 无 stream 能力（`respondStream` 已删） | 恢复 stream 发送，并加滚动续窗 |
| `DigestBuffer` 每窗 flush 清空 | 改为累积（只追加），供全量替换刷新 |
| 终稿 markdown 分片、频控账本、断线重试 | **保留**，这几块已验证可用 |

### 2.4 影响范围

- **恢复**：`src/wecom/ws.ts` 的 `respondStream`（markdown 发送保留，两者并存）。
- **新增**：进度气泡推送器（滚动 stream.id、节流、追加语义）。
- **改写**：`src/wecom/transcript.ts` 的 `DigestBuffer` → 累积式进度缓冲；`bridge.ts` 的窗口驱动改为「刷新一条气泡」而不是「下发一条卡片」。
- **保留不动**：`ReplyChannel`（频控账本 / 两级优先级 / 断线重试）、`ReplyAccumulator`、`chunkMarkdown`、工具行压缩、指令回复走 markdown。
- **不改**：主服务任何路由、runHub、agentService、网页前端；企微指令语义与 binding。

## 3. 方案设计

### 方案 D：全 markdown（已实施后否决）

一帧 stream 都不发，进度按 3 秒一条 markdown 卡片。彻底消除动画与 10 分钟窗，但**离散卡片太多太打扰**——这是实跑后用户明确否决的原因，也是本文翻盘的依据。

### 方案 B：进度 stream + markdown 终稿（选定）

- **思路**：一条 stream 气泡承载过程，只追加、每步一行；run 结束时 finish 该气泡，再把正文作为 markdown 终稿发出（必要时分片）。
- **为什么进度适合 stream**：过程信息的价值在「当前进行到哪」，天然适合原地刷新；而它内容极短（一步约 20~30 字符），逐字动画的成本可以忽略。
- **为什么正文必须 markdown**：正文动辄几千字符，走 stream 就会有几十秒的动画滞后；而 markdown 无动画，且不受 10 分钟窗约束，长轮次照样送达。
- **10 分钟窗怎么处理**：不再是硬截止。到点（或行数过多）就 finish 当前气泡、开新 `stream.id` 接着刷（〈决策·stream-rollover〉）。
- **代价**：要同时维护两种 msgtype 与滚动状态机，比方案 D 复杂；进度气泡的行数上限、滚动阈值都是新的调参点。
- **工作量**：S~M（终稿、账本、工具行压缩已完成且验证过，只需换掉进度那一路）。

### 最终选定

**方案 B**。方案 D 的进度形态被实跑否决，但它带来的三件东西全部留用且已验证：markdown 终稿无动画、20480 字节分片、频控账本与断线重试。

### 执行步骤

总原则：**先恢复能力，再换驱动，最后调阈值**。

1. **`ws.ts` 恢复 `respondStream`** — 与 `respondMarkdown` 并存。因为后续两步都要它。
2. **进度推送器** — 持 `stream.id`、节流、`finish`、滚动换气泡。独立成类，因为滚动状态机与渲染、与 SSE 消费都不该纠缠（详见 〈决策·stream-rollover〉/〈决策·progress-throttle〉）。
3. **`DigestBuffer` 改累积** — flush 清空语义改为「渲染全量」。注意 thinking 的一段只算一行这条要保留（详见 〈决策·thinking-one-line〉）。
4. **`bridge.ts` 换驱动** — 定时器不再「下发卡片」而是「刷新气泡」；run 结束时**先 finish 进度气泡再发终稿**（详见 〈决策·final-last〉）。
5. **阈值实跑调参** — 刷新间隔、单气泡行数上限、滚动阈值（详见 〈未决·progress-knobs〉）。

### 压力测试（只保留暴露了新设计点的行）

| 压力维度 | 具体场景 | 方案表现 | 防御性设计 |
|----------|---------|----------|------------|
| 规模压力 | 300 次工具调用的长轮次 | 追加式进度气泡无限长大，动画成本与气泡体积一起失控 | 单气泡行数上限，到顶就滚动开新气泡（〈决策·stream-rollover〉） |
| 规模压力 | 刷新间隔调小 | stream 每帧计 1 条，2 秒即顶满 30 条/分钟 | 节流下限 3 秒 + 频控账本预留终稿额度（〈决策·progress-throttle〉/〈决策·digest-budget〉） |
| 顺序 | 终稿与进度刷新几乎同时 | 正文之后又冒出进度更新 | 终稿前先停节流并 `finish` 进度气泡（〈决策·final-last〉） |
| 断线 | WS 断在 run 中间 | req_id 重连后仍可用（已实测），但旧 `stream.id` 能否继续刷未知 | 重连后一律开新 stream.id，不赌旧气泡（〈未决·stream-id-across-reconnect〉） |
| 长度 | 分片按字符而非字节 | 中文 3 字节/字，必然低估、撞 40058 被**整条拒收** | 分片一律 `Buffer.byteLength`（〈决策·final-chunk〉） |
| 隐私 | 工具 args 流向企微 | 本机绝对路径外泄面扩大 | 路径按 cwd 收成相对路径；thinking 正文一律不发（〈决策·thinking-one-line〉） |

### 5.1 已定决策 / 约束

| 名字 | 结论 | 来源 | 影响位置 |
|------|------|------|----------|
| 决策·stream-progress-markdown-final | 过程走**一条** stream 气泡原地刷新，正文走 markdown 终稿。两种 msgtype 并存 | 用户 2026-08-06 下午（否决全 markdown 的离散卡片） | §0、任务#1/#2/#4 |

| 决策·stream-rollover | 进度气泡在「距首帧约 9 分钟」或「行数/字节到顶」时 `finish` 当前气泡并开新 `stream.id` 续刷。因为 10 分钟窗是 stream 自身属性，而同 req_id 可连发已实测 | §3 压测 + 〈决策·multi-markdown-ok〉 | 任务#2 |

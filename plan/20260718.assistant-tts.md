# 每轮 Assistant 回复 TTS（口语化 + 流式播放）

> **文档定位**：活 spec（会随实施反复更新）。「关键决策与未决项」表是唯一真相源，正文引用它、不复述。
>
> **流水线翻盘**：口语化/TTS 管道已改为「流式分句 + 串行单句合成」，见 [`plan/20260718.tts-streaming-sentences.md`](./20260718.tts-streaming-sentences.md)。本文仍保留挂载点、缓存键、SSE/二次播放等产品面约定；其中 〈决策·rewrite-then-tts〉「整段改写」以新文档为准。

## 0. 一页纸（骨架先行）

- **一句话**：给每个 finished run 的最后一条 assistant 正文加按需 TTS——先经 llm-proxy 口语化，再经 MiMo 流式合成，按 `runId` 落盘缓存，前端边收边播。
- **承重决策**：
  1. **方案 A** —— 整段口语化后再流式 TTS；传输用自家 SSE（pcm16 base64）；缓存命中改走 wav 文件。因为网关流式契约已验证，且与现有 SSE 风格一致，复杂度可控（详见 §3）。
  2. **输入源** —— 只取该 run 最后一条 `assistantMessage` 正文，不含 thinking/工具调用。因为产品要「播 AI 回复」，挂载点也已对齐最后一条 assistant 气泡（详见 〈决策·input-last-assistant〉）。
  3. **缓存键 = `runId`** —— 文件 `data/tts/<runId>.wav`；undo/delete 同步删。因为历史 API 已有 `runId`，且与「一轮提问+应答」粒度一致（详见 〈决策·cache-by-runId〉）。
  4. **首播禁止 seek，命中缓存后开放拖动** —— 流式 pcm 用 Web Audio；完整 wav 用 `<audio>`。因为生成中总时长未知，强行 seek 体验差（详见 〈决策·seek-after-cache〉）。
  5. **同 runId 单飞** —— 并发点击共享一次生成，避免双写坏文件（详见 〈决策·single-flight〉）。
- **验收总目标**：历史与直播收尾后的每轮末条 assistant 有播放按钮；首次点击在口语化结束后开始出声（不等整段音频合成完）；再次点击同轮可暂停/拖动；undo/delete 清理对应文件；失败可感知可重试且不留坏缓存。

## 1. 需求背景

### 1.1 原始需求

> 给每个轮的最后一个 assistant message 增加 TTS：AI 回复完成后底部有播放按钮；点击后为该回复生成口语化音频；前端用进度条暂停和拖动。后端读取回复 → 大模型转口语 → TTS → 传前端。历史轮次也要能播，按 turn ID 缓存。需要支持流式，不能等整段音频生成完再播。撤销时同步删缓存。

### 1.2 背景与动机

长 Markdown 回复适合扫读，也适合「听一遍」；口语化避免把代码块/标题符号硬读出来。按需生成控制成本与延迟。

### 1.3 目标与验收标准

- [ ] 每轮（含历史重开）最后一条 assistant 气泡底部有播放控件。
- [ ] 首次：口语化完成后开始出声，无需等整段 TTS 结束。
- [ ] 再次同 `runId`：走缓存，可暂停与拖动。
- [ ] `undo` 末轮 / `deleteAgent`：对应音频文件删除。
- [ ] 生成失败：UI 错误态 + 可重试；磁盘无残缺正式文件（详见 〈决策·atomic-cache-write〉）。

### 1.4 约束与前提

- 单用户自托管 MVP；不接 Cursor Agent 做改写/TTS（对齐 `titleService` 解耦模式）。
- 底层走本机 llm-proxy（`127.0.0.1:4001/v1`）；MiMo TTS 经网关模型名 `mimo/mimo-v2.5-tts`（详见 〈决策·external-mimo-stream〉）。
- 静态前提：前端无打包器；后端 Express + tsx；不引入重型前端框架。

## 2. 现状分析

### 2.1 相关代码/系统现状

- **挂载点**：直播结束在最后一条 assistant 气泡上 `appendRunMeta`；历史 `renderHistory` 同样只在每 run 最后一条 assistant 上挂 meta。TTS 按钮应与 meta 同级挂载。
- **`runId`**：`getConversationHistory` 已返回 `run.runId`；前端渲染未写入 DOM——实施时需补 `data-run-id`。
- **抽文**：`run.conversation()` → steps 中最后一条 `type === "assistantMessage"` 的 `message.text`。
- **口语化先例**：`titleService` 调 llm-proxy `/chat/completions`，失败不影响主对话。
- **撤销/删除**：`undoLastTurn` / `deleteAgent` 直接改 SqliteLocalAgentStore；无音频清理钩子。
- **直播收尾**：`finished` 后 `refetchConversation` 整页重绘——控件必须出现在历史渲染路径，不能只挂直播瞬时 DOM。

### 2.3 现状与目标的差距

| 现状 | 目标 |
|------|------|
| 无 TTS API / 无缓存目录 | `ttsService` + `data/tts/` + POST/GET |
| DOM 无 `runId` | 气泡可定位到 run |
| 无流式音频播放器 | Web Audio（首播）+ `<audio>`（缓存） |
| undo/delete 不碰磁盘音频 | 同步删缓存 |

### 2.4 影响范围

- **新建**：`src/ttsService.ts`；`public/ttsPlayer.js`（或等价模块）。
- **修改**：`src/server.ts`；`undo`/`delete` 调用链；`public/render.js` / `stream.js`（挂按钮；`done` 后依赖 refetch 即可）；`.gitignore`；可选 `deploy/supervisor.ini` 环境变量注释。
- **不改**：`@cursor/sdk` Agent 循环、`runHub` 主对话 SSE。

## 3. 方案设计

### 方案 A：整段改写 → SSE 推 pcm → Web Audio（选定）

- **思路**：点播放 → 有 `data/tts/<runId>.wav` 则 `GET` 用 `<audio>`；否则 `POST` 开 SSE：status(rewriting) → 口语化完成 → status(synthesizing) → 转发 MiMo pcm16 chunk → 边推边写入 tmp → 成功 rename 为 wav → `done`。前端 Web Audio 排队播放；生成中只播/暂停。
- **改动范围**：见 §2.4。
- **优点**：契约已实测；与现有 SSE 习惯一致；缓存后拖动简单。
- **缺点**：口语化完成前无声音；首播不可任意 seek。
- **工作量**：M

### 方案 B / C（未选）

- B：按句切开改写+TTS——首音更早，实现 L，句间衔接风险高。
- C：裸二进制 chunked pcm——带宽略省，状态/错误通道弱于 SSE。

### 最终选定

**方案 A**（用户 Phase 3 确认）。

### 执行步骤

原则：**可失败的外部调用与原子落盘先于 UI 打磨；历史渲染路径优先于直播瞬时挂载**（因 refetch 会冲掉瞬时 DOM）。

1. **`ttsService` 核心**（先有可脚本验证的抽文/改写/合成/缓存，再接 HTTP）——避免 UI 联调时还在猜网关契约。
2. **HTTP：`POST /api/tts/stream` + `GET /api/tts/:runId`** —— 统一鉴权参数形态（`cwd`+`agentId`+`runId`），与现有 API 一致。
3. **undo / deleteAgent 钩子** —— 在 SQLite 删除成功后删文件，避免库已无 run 但音频残留。
4. **前端：`data-run-id` + 控件 + `ttsPlayer`** —— 挂在 `appendRunMeta` 旁；区分「流式首播」与「缓存播放」两条路径（详见 〈决策·seek-after-cache〉）。
5. **gitignore + typecheck** —— `data/` 不入库；`npm run typecheck` 通过。

### 压力测试（残余风险）

| 压力维度 | 场景 | 方案表现 | 防御 |
|----------|------|----------|------|
| 故障容错 | 改写/TTS 中途失败 | 不 rename 正式文件 | 〈决策·atomic-cache-write〉 |
| 并发 | 同 runId 连点 | 双写风险 | 〈决策·single-flight〉 |
| 规模 | 超长 Markdown | TTS 过长/贵 | 〈决策·text-truncate〉 |
| 前端生命周期 | refetch 重绘 | 按钮消失 | 挂历史渲染路径 |
| 播放 UX | 流式中拖动 | 总时长未知 | 〈决策·seek-after-cache〉 |

## 4. 实施计划

### 4.2 测试要点

- [ ] 短回复：首播有声；二次播放走缓存可 seek。
- [ ] 含代码块的长 Markdown：口语化后朗读自然；触发截断时有提示或静默截断符合 〈决策·text-truncate〉。
- [ ] 连点播放：只生成一次。
- [ ] 生成中断网/关 SSE：无正式 wav；可重试。
- [ ] 撤销末轮：按钮与文件皆无。
- [ ] 删除会话：该 agent 相关缓存清理（详见 〈决策·delete-agent-tts〉）。
- [ ] 回归：普通发消息 / 历史打开 / undo 主路径不受影响。

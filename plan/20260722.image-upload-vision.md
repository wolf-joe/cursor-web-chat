# 图片上传并提交给 Vision 模型

> **文档定位**：**活 spec**（会随实施反复更新）。「关键决策与未决项」表是唯一真相源，正文引用它、不复述。

## 0. 一页纸（骨架先行）

- **一句话**：在 composer 支持粘贴/选图，经 JSON base64 交给 `@cursor/sdk` 的 `send({ text, images })`，并按 `runId` 旁路落盘以便刷新后用户气泡仍能显示缩略图。
- **承重决策**：
  1. **方案 A：单请求直通 + runHub 落盘** —— 与现有「发起即返回 + attach」一致，一次往返，`runId` 与旁路键天然对齐（详见 §3）。
  2. **必须图文同发** —— 有图时 `text` 非空，保证新会话标题与产品语义；禁止仅图（详见 〈决策·text-required-with-image〉）。
  3. **旁路存储键 = `runId`** —— SDK `conversation()` 的 `UserMessage` 只有 `text`、回不了图；UI 只信 `GET /api/user-images/:runId`（详见 〈决策·side-store-by-runId〉）。
  4. **Vision 闸门** —— 白名单除 `glm-5.2` 外可带图；前后端双检（详见 〈决策·vision-allowlist〉）。
  5. **传输用 base64 JSON** —— MVP 不引入 multipart/临时 `imageId`；抬高 `express.json` limit（详见 〈决策·json-base64〉）。
- **验收总目标**：vision 模型下一轮可带 1 张 ≤5MB 图并与文字同发；直播重连与历史刷新用户气泡有缩略图；undo/delete 清旁路文件；非 vision / 非法输入被明确拒绝；纯文字路径无回归。

## 1. 需求背景

### 1.1 原始需求

> 我希望在前端增加一个图片上传的功能，并且提交给大模型。

后续确认：剪贴板粘贴 + 移动端加号选图；一轮最多一张、≤5MB；刷新后缩略图；仅 vision 模型；旁路存储；base64；除 GLM 5.2 外均支持 vision；**不允许只发图**（须图文同发）。

### 1.2 背景与动机

用户要把截图/相册图交给 agent 做视觉理解，并可继续调工具改代码；现有链路纯文本，文件浏览的 `@路径` 也不会把图像素交给模型。

### 1.3 目标与验收标准

- [ ] 入口：composer 加号（`input[type=file] accept=image/*`）+ 剪贴板粘贴；预览可移除；一轮最多 1 张。
- [ ] 发送：图文同发进 `agent.send({ text, images })`；模型能基于图回答/调工具。
- [ ] 直播中刷新：用户气泡有文字 + 缩略图（`attach` 带 `imageUrl`）。
- [ ] 历史重开：用户气泡仍有缩略图（旁路 GET）。
- [ ] undo 末轮 / delete agent：对应旁路文件删除（与 TTS 同钩子）。
- [ ] 非 vision（`glm-5.2`）、超大、非法 mime、有图无字：明确错误；纯文字无回归。

### 1.4 约束与前提

- 单用户自托管 local 运行时；不接 cloud；前端无打包器/无新框架依赖。
- 不扩展文件浏览「以图片发送」；本需求只做 composer 上传（详见 〈决策·no-file-browser-image-send〉）。
- 易变结论（mime 列表、body limit、目录名、vision 集合）一律以 §5 为准。

## 2. 现状分析

### 2.1 相关代码/系统现状

- **发送**：`POST /api/chat` 要求 `text`；`sendMessage` → `agent.send(text, { model, mode: "agent" })` 只传 string。
- **直播**：`runHub.startRun(agentId, run, userText, cwd)`；`attach` 只补发 `userText`。
- **历史**：`listRuns` + `conversation()` + `messages.list` 补 `userMessage.text`；前端用户气泡只渲染文本。
- **SDK**：`SDKUserMessage` 支持 `images?: SDKImage[]`（`data`+`mimeType` 或 `url`）；但 `conversation()` 侧 `UserMessage` schema **仅 `text`**。
- **模型**：`MODELS_CONFIG.allowed` 无 vision 标记；`models-catalog.json` 无 capability 字段。
- **旁路先例**：TTS 按 `runId` 落 `data/tts/`，undo/delete 同步清理——图片复用同一生命周期钩子。
- **Body**：`express.json()` 默认约 100KB，无法承载 5MB 图的 base64。

### 2.3 现状与目标的差距

| 现状 | 目标 |
|------|------|
| 无选图/粘贴 UI | 加号 + paste + 预览 |
| `send(string)` | `send({ text, images })` |
| 无图持久化 | `data/user-images/<runId>` + GET |
| attach 仅文本 | attach 可选 `imageUrl` |
| 无 vision 标记 | `supportsVision` 暴露给前端 + 服务端闸门 |
| json ~100KB | limit 按 〈决策·json-body-limit〉 |

### 2.4 影响范围

- **新建**：旁路模块（读写/删，类比 `ttsService` 的缓存路径助手）；可选薄封装放在独立文件。
- **修改**：`src/config.ts`、`src/models.ts`、`src/agentService.ts`、`src/runHub.ts`、`src/server.ts`；`public/composer.js`、`api.js`、`stream.js`、`render.js`、`index.html`、`style.css`、`dom.js`；undo/delete 清理链。
- **不改**：agent 主循环协议形态、cloud、文件浏览 Overlay、TTS 管道本身。

## 3. 方案设计

### 方案 A：单请求 JSON base64 + runHub 旁路落盘（**选定**）

- **思路**：前端选图 → FileReader/base64 → 与文字一次 `POST /api/chat`；服务端校验 vision/mime/大小/非空 text → `send({ text, images })` → 用 `run.id` 原子写入旁路文件 → `attach` 带 `imageUrl`；历史按 `runId` GET 显示。
- **改动范围**：见 §2.4。
- **优点**：贴合现有 chat/runHub；一次往返；键与 TTS 一致。
- **缺点**：大 JSON 移动网慢；失败须整包重传（可接受于 MVP）。
- **工作量**：M

### 方案 B：先上传 `imageId` 再 chat（未选）

多一轮临时文件生命周期，MVP 过重。

### 方案 C：旁路只存缩略图（未选）

需图像处理依赖；本期存原图供 `<img>` 缩略展示即可（CSS 限制显示尺寸）。

### 方案对比

| 维度 | A | B | C |
|------|---|---|---|
| 改动范围 | 中 | 大 | 中+图像处理 |
| 回归风险 | body limit / attach 形状 | 临时文件竞态 | 解码依赖 |
| 工作量 | M | L | M–L |

### 最终选定

**方案 A**（用户 Phase 3 确认）。

### 执行步骤

原则：闸门与旁路先落地，再接通 SDK，最后接 UI——可失败校验前置，不可逆/用户可见能力殿后。

1. **config + `/api/models` 暴露 `supportsVision`** —— 前后端共用 〈决策·vision-allowlist〉，避免各猜一份。
2. **旁路读写 + undo/delete 清理** —— 不依赖 chat 即可测 GET/删；钩子对齐 TTS。
3. **`sendMessage` + `/api/chat` + `express.json` limit** —— 校验通过后 `send`；`run.id` 已知后写盘；写盘失败不回滚 run（详见 〈决策·persist-best-effort〉）。
4. **`runHub`：`attach` 增加可选 `imageUrl`（及必要时 `runId`）** —— 写盘完成后再接受订阅，避免重连抢在落盘前。
5. **前端 composer：加号 + paste + 预览 + 发送校验** —— 非 vision 禁用；有图无字禁发。
6. **`render` / `stream`：用户气泡缩略图** —— 直播与历史同一套 DOM（`img` src = 旁路 URL）。
7. **`npm run typecheck` + §4.2 手测**。

### 压力测试（残余风险）

| 压力维度 | 具体场景 | 方案表现 | 防御 |
|----------|---------|----------|------|
| 故障容错 | send 成功、写盘失败 | 对话可用、刷新无图 | 〈决策·persist-best-effort〉；UI 可无图降级 |
| 规模 | 顶格 ~7MB JSON | 默认 100KB 会莫名失败 | 〈决策·json-body-limit〉 |
| 外部契约 | conversation 无 images | 刷新丢图 | 〈决策·side-store-by-runId〉；UI 不解析 SDK 历史图 |
| 操作 | undo/delete 漏删 | 磁盘残留 | 与 TTS 同钩子清理 |

## 4. 实施计划

### 4.1 子任务拆解

| # | 任务 | 涉及文件/模块 | 验收标准 | 优先级 |
|---|------|---------------|----------|--------|
| 1 | vision 标记进 config / models API | `config.ts`、`models.ts`、前端模型栏 | 按 〈决策·vision-allowlist〉；前端能读 `supportsVision` | 必须 |
| 2 | 旁路存储 CRUD + 路径防穿越 | 新模块或 `userImageStore`；`server` GET | 按 〈决策·side-store-by-runId〉 读写删 | 必须 |
| 3 | undo / delete 清图片 | `server.ts`（对齐 TTS） | 撤销/删会话后文件不在 | 必须 |
| 4 | chat + sendMessage 接 images | `server.ts`、`agentService.ts` | 图文进模型；校验按 §5 | 必须 |
| 5 | runHub attach 带 imageUrl | `runHub.ts`、`stream.js` | 刷新重连用户气泡有图 | 必须 |
| 6 | composer 加号/粘贴/预览 | `index.html`、`composer.js`、`dom.js`、`style.css`、`api.js` | 入口与校验符合 §1.3 | 必须 |
| 7 | 历史用户气泡缩略图 | `render.js` | 重开会话仍显示 | 必须 |
| 8 | typecheck + 手测 | — | §4.2 勾完 | 必须 |

### 4.2 测试要点

- [ ] vision 模型：粘贴 / 加号各成功一轮；模型能描述图或按图调工具。
- [ ] 有图无字、超 5MB、非允许 mime、`glm-5.2` 带图：前端拦截 + 服务端 400。
- [ ] 发送中刷新：文字 + 缩略图。
- [ ] finished 后重开历史：缩略图仍在。
- [ ] undo 末轮、删除会话：旁路文件删除。
- [ ] 纯文字多轮：无回归（含标题生成）。
- [ ] 切换到 `glm-5.2` 时已选图被清空或无法发送。

### 4.3 首跑策略

**触发判断**：涉及 Cursor 付费/按量 agent 调用 —— **是**（与平时对话同档）。

**首跑铁律**：

- [ ] 先用最小 PNG（数 KB）+ 短文本跑通一轮，再试接近 5MB。
- [ ] 确认旁路文件出现、`GET` 可开、undo 后消失。
- [ ] 再在手机上验加号选图。

**本次首跑配置**：

- 最小样本：本地小图 + 「图里有什么」类短句
- fixture：不强制；若 SDK 报错需保留响应日志便于对照
- 成本：与普通一轮 agent 相当；勿批量刷大图

## 5. 关键决策与未决项（唯一真相源）

### 5.1 已定决策 / 约束

| 名字 | 结论 | 来源 | 影响位置 |
|------|------|------|----------|
| 方案选型 | 单请求 JSON base64 + runHub 旁路落盘（方案 A） | 用户 Phase 3 | §0、§3、任务#4–6 |
| text-required-with-image | 有图时必须非空 `text`；禁止仅图 | 用户（标题/语义） | `/api/chat` 校验、composer 发送条件 |
| side-store-by-runId | 图片旁路 `data/user-images/<runId>`（扩展名由 mime 映射）；UI 只经 GET；不依赖 SDK 历史回图 | Phase 2 源码 + 用户确认 | 旁路模块、render/stream、undo/delete |
| vision-allowlist | 当前 `allowed` 中除 `glm-5.2` 外均 `supportsVision`；名单随 config 维护 | 用户 | `config.ts`、`/api/models`、前后端闸门 |
| json-base64 | 图以 `{ mimeType, data }` base64 放在 chat JSON body，不走 multipart | 用户 | `api.js`、`/api/chat`、`express.json` |

| max-one-image-5mb | 一轮最多 1 张；解码后原始字节 ≤5MB | 用户 | 前后端校验 |
| allowed-mime | `image/png` \| `image/jpeg` \| `image/webp` \| `image/gif` | Phase 3 草案（用户未改即定） | 校验、落盘扩展名 |
| persist-best-effort | 旁路写盘失败只打日志、不回滚已建立的 run；attach 无 `imageUrl` | Phase 3 压测 | `runHub` / chat 落盘路径 |

| entry-paste-and-plus | 入口：剪贴板粘贴 + 加号选系统图库 | 用户 | composer / index.html |

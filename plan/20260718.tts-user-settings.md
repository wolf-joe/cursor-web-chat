# TTS 用户设置（自动朗读 + 播放时常亮）

> **文档定位**：**活 spec**（会随实施反复更新）。
> 「关键决策与未决项」表是唯一真相源；正文引用它、不复述它。

## 0. 一页纸（骨架先行）

- **一句话**：在右上角 ⋮ 增加用户级「TTS 设置」modal——自动在刚结束的一轮后朗读、播放期间尽量保持屏幕常亮；设置只存浏览器 localStorage。
- **承重决策**：
  1. **方案 A：纯前端** —— 不改后端/`done` 载荷；自动播挂在 refetch 之后，因为控件与 `runId` 本来就只在 `renderHistory` 出现（详见 §3 / 〈决策·auto-after-refetch〉）。
  2. **两开关、用户级** —— `autoTts`（默认关）+ `keepAwakeWhileTts`（默认开）；入口在选了文件夹后的 ⋮（详见 〈决策·two-toggles〉〈决策·menu-requires-cwd〉）。
  3. **只对刚结束这一轮** —— 等同点 ▶；历史打开不自动播；旁观接入同一 `done→refetch` 路径也播（详见 〈决策·just-finished-only〉）。
  4. **常亮跟播放生命周期** —— Screen Wake Lock；loading/streaming/播放中持有，暂停/结束/停止/出错释放；不支持则静默降级（详见 〈决策·wake-lock-lifecycle〉）。
- **验收总目标**：设置可持久；自动 TTS 开时本轮正常结束后自动开读；常亮开时播放期间尽量不灭屏；关开关则行为回到今日。

## 1. 需求背景

### 1.1 原始需求

> 用户级设置，放在网页右上角三个点菜单；用 modal 做 TTS 设置。可开关：默认所有对话结束后自动启用 TTS；TTS 播放时前台网页保持常亮，不要让手机进灭屏。

后续确认：选了文件夹才能进设置；只对刚结束这一轮（等同手动点 ▶）；旁观接入也要；常亮跟播放走；自动 TTS 默认关；常亮默认开；就这两个开关；选定方案 A。

### 1.2 背景与动机

TTS 已是按需按钮（`plan/20260718.assistant-tts.md`）。手机上听回复时每次手动点、且屏幕易灭，打断收听。用户级开关把「听完这一轮」收成默认习惯，且不绑会话、不脏写服务端。

### 1.3 目标与验收标准

- ⋮ →「TTS 设置」；两开关；刷新后仍在（〈决策·two-toggles〉）。
- 自动关：与今日相同。
- 自动开：`finished`/`unknown` 且 refetch 成功后自动播末轮；含旁观；打开历史不播（〈决策·just-finished-only〉〈决策·auto-after-refetch〉）。
- 常亮开：生成/播放中尽量不灭屏；停播后释放；不支持无报错（〈决策·wake-lock-lifecycle〉）。
- 常亮关：不申请 Wake Lock。

### 1.4 约束与前提

- 前端无构建单页；能力落在 `public/`；后端 TTS API / Agent 主循环不动（〈决策·frontend-only〉）。
- 设置用 localStorage，与现有会话/模型持久化同模式。
- 易变键名、默认值收口 §5，正文不复述多份。

## 2. 现状分析

### 2.1 相关代码/系统现状

- **⋮ 菜单**：`index.html` `headerDropdown`；无 cwd 时 `headerMenuBtn` 禁用；现有新建/重命名/撤销/删除。
- **Modal 先例**：`modelParamsModalOverlay`（约 380px）；commit 确认 modal 同类壳。
- **TTS**：`public/ttsPlayer.js`——`appendTtsControls` 挂在 `renderHistory` 每 run 末条 assistant；点 ▶ → `togglePlay`（未导出）。直播 `done` 只 `appendRunMeta`，不挂控件。
- **收尾时序**：`stream.js` `done` →（finished/unknown）`refetchConversation` → `renderHistory`（**开头** `stopTtsPlayback()`）→ 控件出现。`done` 事件**无** `runId`。
- **持久化**：`state.js` 已有 `cursor-web-chat:*` localStorage 键。

### 2.3 现状与目标的差距

| 目标 | 现状 | Gap |
|------|------|-----|
| 用户级 TTS 设置 UI | 无 | 菜单项 + modal + 读写 |
| 结束后自动播 | 仅手动 ▶ | refetch 后触发 `playTts` |
| 播放时常亮 | 无 | Wake Lock 绑播放态 |

### 2.4 影响范围

- **会改**：`public/state.js`、`index.html`、`dom.js`、`app.js`（或独立 `userSettings.js`）、`stream.js`、`ttsPlayer.js`、`style.css`；可选在 `CLAUDE.md` 同页能力表加一行指向本文。
- **不动**：`src/ttsService.ts`、`runHub`、`/api/tts/*`、会话 SQLite。

## 3. 方案设计

### 方案 A：纯前端设置 + refetch 后触发（选定）

- **思路**：localStorage 两开关；⋮ 开 modal；`refetchConversation` 在 `renderHistory` 之后，若 `autoTts` 且仍是同一 agent/cwd，取 `data.runs` 末项 `runId` 调导出的 `playTts`（内部走现有 `togglePlay` 路径）。Wake Lock 全在 `ttsPlayer` 按设置与播放态管理。
- **改动范围**：见 §2.4。
- **优点**：贴合现有时序；发起方与旁观同一路径；后端零改。
- **缺点**：refetch 失败则不自动播（可稍后手动，若 DOM 无控件需重进会话）——已纳入 〈决策·refetch-fail-skip〉。
- **工作量**：S

### 方案 B：`done` 带 `runId` + 直播挂控件（未选）

首音略早、refetch 失败也能播；但要改 `runHub`，且需处理 refetch 时 `stopTtsPlayback` 冲掉同 run 播放。触点多。

### 方案 C：设置存服务端（未选）

单用户单浏览器过重，与现有前端持久化习惯不一致。

### 方案对比

| 维度 | A | B | C |
|------|---|---|---|
| 改动范围 | 仅 public | public + runHub | public + API |
| 时序贴合 | 最好 | 需防冲播 | — |
| 工作量 | S | M | L |

### 最终选定

**方案 A**，用户 Phase 3 选定。

### 执行步骤

原则：**先有设置可读，再接线自动播与常亮；自动播必须在 renderHistory 之后，避免被 `stopTtsPlayback` 冲掉。**

1. **持久化** —— `state.js` 增加 `userSettings` 与 load/persist（键/默认值见 〈决策·storage-key〉〈决策·two-toggles〉），因为后续 UI 与播放器都读同一处。
2. **设置 UI** —— `index.html` 菜单项 + settings modal；`userSettings.js`（或等价）绑定开关即时写入；入口不依赖 `currentAgentId`，只依赖现有「有 cwd 才开菜单」（〈决策·menu-requires-cwd〉）。
3. **导出播放入口** —— `ttsPlayer.js` 导出 `playTts(runId)`，复用现有生成/缓存逻辑，因为自动播必须与手动 ▶ 同路径，避免双实现。
4. **Wake Lock** —— 在 `ttsPlayer` 进入 loading/streaming/cached 且未暂停时 request；pause/ended/`stopAll`/error 时 release；`visibilitychange` 可见且仍在播时重申（〈决策·wake-lock-lifecycle〉）。受 〈决策·two-toggles〉 `keepAwakeWhileTts` 门控。
5. **自动触发** —— `stream.js` `refetchConversation`：`renderHistory` 后检查设置与 agent/cwd 仍匹配，取末 run 的 `runId` 调 `playTts`。仅 finished/unknown 会走到 refetch，故 cancelled/error 自然不播（〈决策·just-finished-only〉）。

### 压力测试（残余风险）

| 压力维度 | 具体场景 | 方案表现 | 防御 |
|----------|---------|----------|------|
| 故障容错 | refetch 失败 / runs 空 | 无自动播 | 〈决策·refetch-fail-skip〉；不重试轰炸 |
| 故障容错 | Wake Lock 拒/无 API | 照常播，只是可能灭屏 | 静默降级，不 toast 打扰 |
| 成本风险 | 自动 TTS 每轮调口语化+MiMo | 用户自担 | 默认关；失败不自动重试 |
| 交互叠音 | done chime 与 TTS 首音接近 | 可接受 | 本轮不改 chime |
| 演进 | 以后加音色/语速 | 扩同一 modal + settings 对象 | 键结构预留对象而非散键亦可，实施时按 〈决策·storage-key〉 |

## 5. 关键决策与未决项（唯一真相源）

### 5.1 已定决策 / 约束

| 名字 | 结论 | 来源 | 影响位置 |
|------|------|------|----------|
| frontend-only | 不改后端 TTS/runHub/`done` 载荷 | 用户选方案 A | §2.4、任务#4 |
| menu-requires-cwd | 设置入口挂现有 ⋮；无 cwd 时菜单仍禁用 | 用户 Phase 1 | 任务#2、`render.js` updateHeaderMenuState |
| two-toggles | 仅 `autoTts`（默认 `false`）与 `keepAwakeWhileTts`（默认 `true`） | 用户确认 | `state.js`、modal、ttsPlayer 门控 |
| storage-key | localStorage 键 `cursor-web-chat:userSettings`，JSON `{ autoTts, keepAwakeWhileTts }` | 实施约定（对齐现有 `cursor-web-chat:*`） | `state.js` |
| just-finished-only | 只对刚结束轮自动播；历史打开不播；旁观同一路径要播；仅 finished/unknown（随 refetch） | 用户确认 | `stream.js` |
| auto-after-refetch | 自动播在 `renderHistory` **之后**；取 `data.runs` 末项 `runId`；播前确认 agentId/cwd 仍匹配 | 源码时序 + 方案 A | `stream.js`、`ttsPlayer.js` |
| wake-lock-lifecycle | 有设置则：loading/streaming/cached 未暂停 → request；pause/ended/stopAll/error → release；visibility 可见且仍播 → 重申；无 API/拒绝静默降级 | 用户确认 + MDN Screen Wake Lock | `ttsPlayer.js` |
| refetch-fail-skip | refetch 失败或无 runId 则跳过自动播，不重试 | Phase 3 压测 | `stream.js` |

# TTS 流式分句口语化 + 串行单句合成

> **文档定位**：活 spec（会随实施反复更新）。「关键决策与未决项」表是唯一真相源，正文引用它、不复述。
> 本需求是对 `plan/20260718.assistant-tts.md` 流水线的翻盘优化：保留按需播放、单 wav 缓存、二次可拖动；翻盘「整段口语化后再整段 TTS」。

## 0. 一页纸（骨架先行）

- **一句话**：点播放后，口语化改为流式并按换行分句，句到齐即串行送 MiMo TTS；句间插静音；边推 pcm 边播；成功后仍落一个 `runId.wav`。
- **承重决策**（3~5 条）：
  1. **方案 A** —— 流式改写 + `\n` 切句 + 串行 TTS，因为要同时压「首音延迟」和「长文一次合成乱读」（详见 §3 / 〈决策·scheme-a-stream-sentences〉）。
  2. **分句只认换行** —— prompt 强制一行一句，后端只按 `\n` 切、空行跳过、不做标点二次切分，因为规则简单且与模型输出契约对齐（详见 〈决策·newline-only-split〉）。
  3. **句间 250ms 静音 + 任一句失败则整 run 失败** —— 避免硬切听感，且不留下半截正式缓存（详见 〈决策·sentence-silence〉 / 〈决策·fail-fast-run〉）。
  4. **首个 pcm chunk 即开播；缓存仍是单个 wav** —— 前端已有 Web Audio 排队；二次播放逻辑不改（详见 〈决策·play-on-first-pcm〉 / 〈决策·cache-one-wav〉）。
- **验收总目标**：长文不再整段乱读；首音早于整段口语化完成；成功落盘后二次播放可拖动；失败无正式 wav；undo/delete 清理不变。

## 1. 需求背景

### 1.1 原始需求

> TTS 目前是 AI 回复后整段口语化，再整段 TTS，端到端延迟大，长文一次合成会声音混乱。希望口语化改成流式，按回车换行分句；流式出句时并行做单句 TTS，降低延迟；拼装本地缓存；前端最好在第一句相关音频就绪后尽早播放。

后续确认：仍点播放才生成；乱读来自长文一次合成；分句只靠口语化模型换行；TTS 严格串行；落一个完整 wav；二次播放保持原逻辑；句间插静音；空行不调 TTS；任一句失败整 run 失败；前端等首句首个 pcm chunk 开播。

### 1.2 背景与动机

现实现（`ttsService`）在口语化整段返回前不发声，且把整段口语文一次交给 MiMo——长文易乱读，短文也白白多等整段改写。按句串行合成 + 改写与 TTS 流水线重叠，可同时改善延迟与朗读质量。

### 1.3 目标与验收标准

- [ ] 短回复：点播后首音明显早于「整段口语化完成」的体感（多句时在首句 TTS 首包即响）。
- [ ] 长回复：不再出现整段一次 TTS 的乱读；句间有可感知短停顿（〈决策·sentence-silence〉）。
- [ ] 空行不调 TTS，不产生额外尖刺停顿。
- [ ] 某句 TTS / 口语化失败：SSE `error`，无正式 `runId.wav`，可重试。
- [ ] 成功后二次点击：走缓存 wav，可暂停/拖动（与现逻辑一致）。
- [ ] undo 末轮 / delete agent：对应音频仍被清理。
- [x] `npm run typecheck` 通过。

### 1.4 约束与前提

- 单用户自托管；口语化与 TTS 仍走本机 llm-proxy，不接 Cursor Agent（与 title/commit 短任务同模式）。
- 触发、缓存键、HTTP 入口形态尽量保持现有 TTS 产品面（详见 〈决策·on-demand-click〉 / 〈决策·cache-one-wav〉 / 〈决策·api-shape-preserve〉）。
- 静态前提：无前端打包器；后端 Express + tsx；不引入重型框架。

## 2. 现状分析

### 2.1 相关代码/系统现状

- **管道**：`POST /api/tts/stream` → `streamTts` 单飞 → `extractLastAssistantText` → **非流式** `rewriteForSpeech` → **整段** `synthesizeStreaming` → `pcm16ToWav` 原子落盘 `data/tts/<runId>.wav`。
- **SSE**：`status(rewriting)` → `status(synthesizing)` → `audio(base64 pcm16)` → `done` / `error`。
- **前端** `ttsPlayer.js`：收到 synthesizing / 首包 audio 后用 Web Audio 按 `nextTime` 排队；缓存命中改 `<audio>` 可拖动。
- **清理**：undo / deleteAgent 删对应 wav（及 tmp）。

原活 spec `plan/20260718.assistant-tts.md` 曾明确选「整段改写再 TTS」，并把按句流水线标为未选的方案 B。

### 2.3 现状与目标的差距

| 现状 | 目标 |
|------|------|
| 口语化阻塞至整段完成 | 流式改写，行到齐即入队 |
| 一次 MiMo 吃全文 | 非空句串行 TTS + 句间静音 |
| 首音 ≈ 整段改写完成 + TTS 首包 | 首音 ≈ 首句改写完成 + 该句 TTS 首包 |
| 缓存 / 二次播放 / 点播触发 | 保持 |

### 2.4 影响范围

- **主改**：`src/ttsService.ts`（流水线、prompt、静音 pcm）。
- **小改或不动**：`public/ttsPlayer.js`（确认首 pcm 开播；状态文案微调）。
- **预期不动**：`server.ts` 路由形态、undo/delete 钩子、`GET /api/tts/:runId`、抽文规则、单飞与 atomic 落盘原则。
- **文档**：本文件为实施真相源；原 `assistant-tts.md` 中 〈决策·rewrite-then-tts〉「整段」被本需求翻盘（实施时在原文档加指针或修订结论一行即可）。

## 3. 方案设计

### 方案 A：流式口语化 + 句队列 + 串行 TTS（选定）

- **思路**：`stream:true` 口语化 → 按 `\n` 切非空行入队 → TTS worker 严格串行；句与句之间插入固定静音 pcm；每句 TTS 的 pcm chunk 立刻经现有 SSE 推出；改写可与当前句 TTS 重叠；全部成功后 concat（含静音）写成一个 wav。
- **改动范围**：见 §2.4。
- **优点**：首音最早；对症长文乱读；二次播放与缓存路径不变。
- **缺点/风险**：N 次 TTS 成本上升；依赖模型按行输出；flash 流式契约需先探活。
- **工作量**：M

### 方案 B：整段口语化后再按行串行 TTS（未选）

- 只修乱读，不修改写阻塞首音；工作量 S，延迟收益不足。

### 方案 C：同 A + 句级 SSE 事件（未选）

- 可观测性更好，当前产品不需要句进度 UI；协议更重。

### 最终选定

**方案 A**（用户 Phase 3 确认）。

### 执行步骤

原则：**可失败的外部流式探活前置；管道核心先于前端文案**。

1. **探活 flash 流式** —— 对 `LLM_PROXY_FLASH_MODEL` 短文本 `stream:true`，确认 `choices[0].delta.content` 可用且能拼出带换行文本；失败则停，避免整条管道建在错误契约上（详见 〈决策·external-rewrite-stream〉）。
2. **改口语化 system prompt** —— 强制一行一句、换行分隔、直接出口语正文（详见 〈决策·rewrite-prompt-lines〉）。
3. **重写 `ttsService` 流水线** —— 流式改写缓冲按 `\n` 切句；空行跳过；串行 TTS；句间插静音；边推 `audio`；成功才 atomic rename；保留单飞 / 抽文 / 删除 API（详见 〈决策·scheme-a-stream-sentences〉 等）。
4. **前端对齐** —— 首个 `audio` 即 streaming 开播；必要时把「口语化…」在首包后改为「朗读中…」；缓存路径不动。
5. **typecheck + 手动验收** —— 按 §1.3 / §4.2。

### 压力测试（残余风险）

| 压力维度 | 场景 | 方案表现 | 防御 |
|----------|------|----------|------|
| 故障容错 | 第 K 句 TTS 失败（此前已推过 pcm） | 前端可能听到半截后 `error`；不落正式 wav | 〈决策·fail-fast-run〉〈决策·atomic-cache-write〉；重试重新生成 |
| 外部契约 | flash 不流式或字段不符 | 管道无法启动 | 步骤 1 探活；〈决策·external-rewrite-stream〉 |
| 规模 / 听感 | 模型吐超长单行 | 该句仍可能乱读 | 〈决策·no-secondary-split〉；靠 prompt；〈决策·long-line-warn〉仅 Warning |
| 成本 | 长文 N 次 TTS | 费用高于一次整段 | 保留 〈决策·text-truncate〉；空行跳过 |

### 4.2 测试要点

- [ ] 短文 1–2 句：可播；句间停顿不明显刺耳。
- [ ] 长 Markdown：口语化后多行；朗读连贯、无整段乱读。
- [ ] 口语化结果含空行：不额外调用 TTS。
- [ ] 模拟中途 TTS 失败：无正式 wav；可再点重试。
- [ ] 成功后再点：HEAD/GET 缓存，可 seek。
- [ ] undo / delete：文件清除。
- [ ] 回归：主对话发消息 / 历史打开不受影响。

### 4.3 首跑策略

**触发判断**：涉及按量网关调用 —— **是**（口语化 token + N 次 MiMo TTS）。

**首跑铁律**：

- [ ] 先完成 flash 流式探活（任务#1），再改管道。
- [ ] 联调先短文本单 run，再长文。
- [ ] 本仓库无测试套件；不强制 commit 音频 fixture；以日志 + 听感验收。

**本次首跑配置**：

- 最小样本：两三句中文、带换行预期的短回复 run。
- 单次成本：1 次 flash 流式 completion + 每句 1 次短 TTS；最坏由单飞限制为同一 runId 一条流水线。

## 5. 关键决策与未决项（唯一真相源）

### 5.1 已定决策 / 约束

| 名字 | 结论 | 来源 | 影响位置（改它要动哪） |
|------|------|------|----------------------|
| scheme-a-stream-sentences | 流式口语化 + `\n` 切句 + 串行 TTS；改写与当前句 TTS 可重叠 | 用户 Phase 3 选 A | §0、§3、任务#2 |
| newline-only-split | 只按换行切分；不做标点二次切分 | 用户 Phase 1–2 | `ttsService` 切句逻辑 |
| skip-blank-lines | 空行/纯空白不调 TTS | 用户 Phase 2 确认 | 切句入队 |
| sentence-silence | 非空句之间插入 250ms 零 pcm（24kHz）；首句前、末句后不插 | 用户 Phase 3 默认确认 | `ttsService` 拼接 / 推流 |
| fail-fast-run | 口语化失败或任一句 TTS 失败 → 整 run 失败；不 rename 正式 wav；删 tmp | 用户确认 | `runPipeline`、SSE error |
| play-on-first-pcm | 前端在首个 `audio` chunk 即开播（不必等整句 TTS 结束） | 用户确认 | `ttsPlayer.js` |
| cache-one-wav | 仍 `data/tts/<runId>.wav`；二次播放 GET wav + 可拖动 | 用户 Phase 1 | 落盘、前端 cached 路径 |
| on-demand-click | 仍点播放才生成，不自动播 | 用户 Phase 1 | 产品触发 |
| api-shape-preserve | 尽量保持现有 SSE 事件类型（status/audio/done/error）与 POST/GET 路由；不强制句级事件 | Phase 3 选 A 非 C | `server.ts`、前端解析 |
| rewrite-prompt-lines | system：去 Markdown/代码块/URL；**一行一句、换行分隔**；直接出口语文稿 | Phase 3 固化 | `REWRITE_SYSTEM_PROMPT` |
| text-truncate | 抽文后截断再口语化；默认 6000 字符，静默截断 | 继承原 TTS 方案 | `ttsService` |
| single-flight | 同 runId 同时只跑一条生成流水线 | 继承 | `streamTts` |
| atomic-cache-write | 写 `*.tmp` 成功后再 rename；失败删 tmp | 继承 | 落盘 |

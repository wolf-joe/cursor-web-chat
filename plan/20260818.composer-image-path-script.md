# Composer 上传图：清单脚本让 agent 拿到磁盘路径

> **文档定位**：**活 spec**（会随实施反复更新）。「关键决策与未决项」表是唯一真相源，正文引用它、不复述它。

## 0. 一页纸（骨架先行）

- **一句话**：不改上传/写盘/vision，另做只读脚本，把网页 composer 旁路落盘的图和 SQLite 里该轮用户文本对上，让 local agent 用工具去改图/OCR/上传；脚本入口只写在 Global Rules。
- **承重决策**：
  1. **方案 B（收窄）** —— 发现靠全局规则 + 脚本，不往本轮 `text` 注入路径、不把图拷进用户 cwd。因为目标是「工具能摸到已有旁路文件」，不是改发送协议（详见 §3 / 〈决策·scheme-b-script-only〉）。
  2. **写盘链路冻结** —— `/api/chat`、`userImageStore`、`send` 顺序、vision `images` 一律不动。旁路仍是 `data/user-images/<runId>.ext`，send 返回后立刻 `await` 写入（详见 〈决策·no-write-path-change〉〈决策·write-after-send-ok〉）。
  3. **列表以磁盘文件为主键** —— 只列出还存在的旁路文件；用 `runId` 去当前 cwd 的 SDK `index.db` 补 agent/turn/时间，用户原文从该 agent 的 `store.db` checkpoint blob 抽预览（详见 〈决策·disk-primary〉〈决策·user-text-from-blobs〉）。
  4. **发现只放 Global Rules** —— 要对网页上传图做读盘类操作时先跑脚本绝对路径并传入当前工作区 cwd。本仓库 `AGENTS.md` 不承担发现（详见 〈决策·discover-via-global-rules〉）。
  5. **企微不改** —— 桥接仍不带图（详见 〈决策·wecom-out-of-scope〉）。
- **验收总目标**：给定 cwd 跑脚本能列出该工作区仍存在的上传图绝对路径，并尽量带上该轮用户文本预览；undo 后该文件从列表消失；composer 上传与直播缩略图无回归。

## 1. 需求背景

### 1.1 原始需求

> 我在这个里面附着了一张图片给你，你应该是能够看到图片的内容的。但是你应该不清楚这张图片在本机磁盘上的路径。我现在需要你想一个方案，让AI能够知道图片的路径在哪。

后续确认：范围是本仓库网页 composer 上传图（不是 Cursor IDE 附件、不是文件浏览 `@路径`）；动机是让 agent 对图做修改 / OCR / 上传等工具操作；完成标准是本轮能通过 Read 或其它工具感知到该文件；企微不考虑；选定旁路清单脚本，写盘阶段不调整，用户文本走现有历史 SQLite，脚本发现放 Global Rules。

### 1.2 背景与动机

Vision 已经能看见像素，但模型拿不到磁盘路径，也就不能按文件去做改图、OCR、上传。旁路文件其实已经在服务机上，缺的是「怎么发现、怎么对上哪一轮用户话」。

### 1.3 目标与验收标准

- [x] 新增只读脚本：扫旁路图片目录，`--cwd` 限定工作区，输出绝对路径 + 轮次元数据 + 用户文本预览（抽不到则标明，不中断）。
- [x] Global Rules 有一条行动规则：需要对网页 composer 上传图做文件操作时先跑该脚本。
- [x] 不改 `/api/chat`、旁路写盘、undo/delete 清图、vision 发送、企微桥。
- [x] 以磁盘为准：无文件或 undo 已删则不出现。

### 1.4 约束与前提

- 单用户自托管；local agent 不开 sandbox，脚本给出的绝对路径可用 Read/Shell 打开（详见 〈决策·abs-path-tools〉）。
- 旁路目录在 web-chat 仓库 `data/` 下，通常不在用户正在聊的 cwd 里；会话库按 cwd 分库（详见 〈决策·cwd-scoped-join〉）。
- 易变结论一律以 §5 为准。

## 2. 现状分析

### 2.1 相关代码/系统现状

- **发送**：`POST /api/chat` 校验图后 `sendMessage` → `agent.send({ text, images: [{ data, mimeType }] })`。模型只收到像素，`text` 不含路径。
- **落盘**：`send` 返回（run 已建立、已有 `run.id`，轮次未跑完）之后立刻 `writeUserImage`，再 `runHub.startRun`。文件名 = `runId`，目录 = `data/user-images/`。写盘失败 best-effort，不回滚 run。
- **UI**：缩略图只经 `GET /api/user-images/:runId`；`conversation()` 的 UserMessage 仅 `text`，回不了图。
- **历史 SQLite**：每个 cwd 一份 `~/.cursor/projects/.../sdk-agent-store/<md5>/index.db`（`runs` 有 `run_id` / `agent_id` / `turn_number` / 时间 / 助手 `result`，**无用户输入列**）。用户原文在 local 下不在 `conversation()` 里；网页历史用 `messages.list`，配不上时读该 agent `store.db` 的 checkpoint blob（`checkpointUserText.ts`）。找库逻辑与 `scripts/cursor_agents.py` 的 `find_index_db` 相同。
- **清理**：undo 末轮 / delete agent 已删对应旁路文件（与 TTS 同钩子）。
- **文件浏览 `@路径`**：只覆盖工作区里已有文件，不会把 composer 上传变成 cwd 内文件。

### 2.3 现状与目标的差距

| 现状 | 目标 |
|------|------|
| 模型有像素、无路径 | 能列出旁路文件绝对路径并对上用户话 |
| agent 不知道旁路目录/命名 | Global Rules 指向脚本 |
| 写盘/send 已够用 | 保持不动 |

### 2.4 影响范围

- **新建**：`scripts/` 下清单脚本（与 `cursor_agents.py` 并列）。
- **修改**：全局规则源（`AGENTS_GLOBAL_COMMON` / `~/.cursor/skills/global-rule`，按现有同步方式），只加发现规则。
- **不改**：`server.ts` chat、`userImageStore`、`agentService.sendMessage`、runHub、企微、composer、本仓库 `AGENTS.md` 发现职责。

## 3. 方案设计

### 方案 B：只读清单脚本 + Global Rules（**选定**）

- **思路**：遍历旁路图片；`--cwd` 打开该工作区 `index.db`，按文件名 `runId` join `runs`；再打开该 `agent_id` 的 `store.db`，按与 `checkpointUserText.ts` 同源的方式抽用户文本预览。stdout 给人/模型读。全局规则写何时跑、脚本绝对路径、必须传当前工作区路径。
- **改动范围**：见 §2.4。
- **优点**：不碰发送与缩略图；跨轮可按用户话定位；任意 cwd 只要规则注入就能发现。
- **缺点**：模型必须先跑脚本才有路径（软保证）；用户原文抽不到时只有 run 元数据。
- **工作量**：S

未选：A（cwd 落盘 + 注入 `@路径`）、C（A+B 混合）——用户明确要旁路脚本且冻结写盘。

### 执行步骤

原则：只加只读能力；可失败的是「某张图抽不出用户原文」，不得因此改写盘。

1. **脚本** —— 复用 `find_index_db(cwd)`；图片目录默认本仓库 `data/user-images`；join 失败的文件仍输出路径并标明未匹配到该 cwd 的 run（避免把别的工作区的图误当成当前会话的）。因为旁路目录是进程全局的，必须用 cwd 把「当前工作区的 run」筛出来（详见 〈决策·cwd-scoped-join〉）。
2. **用户文本** —— 不把 `runs.result`（助手回复）当作用户话；blob 解析失败则预览为「未能还原用户原文」，仍打印路径（详见 〈决策·user-text-from-blobs〉）。
3. **全局规则** —— 一条行动规则：适用范围 = 本机网页对话 composer 上传图、且要对文件做操作时；提醒 = 路径在服务旁路目录不在当前 git 树。不写教程、不为写盘时序写「重试」。
4. **验收** —— 对已有附图的 cwd 跑脚本应对得上；undo 后消失；纯文字轮不出现。

### 压力测试

| 压力维度 | 具体场景 | 方案表现 | 是否需要防御性设计 |
|----------|---------|----------|------------------|
| 外部契约 | 误以为 `runs` / `run_events` 有用户原文列 | 会对错轮或空白 | 用户原文只走 `store.db` blob（〈决策·user-text-from-blobs〉）；抽失败降级不中断 |
| 故障容错 | 旁路 best-effort 写盘失败 | 盘上无文件，列表无此项；vision 仍可能看见像素 | 以磁盘为准即可，不改写盘语义 |
| 规模压力 | 旁路目录堆积 | 全量扫仍便宜；输出过长干扰模型 | 默认只列最近 N 张（〈决策·list-cap〉） |
| 演进兼容 | 以后若改成 cwd 内落盘 | 脚本按目录约定扫，规则仍指向同一入口 | 目录默认值收口在脚本，规则只记命令 |

已排除：send 与写盘之间的窗口不足以让「第一次跑脚本列不到当前图」成为产品问题（〈决策·write-after-send-ok〉），全局规则不为此写重试。

### 4.2 测试要点

- [ ] 某 cwd 下曾用 composer 传过图：脚本给出绝对路径，预览能对上该轮用户话（或明确未能还原）。

- [ ] 回归：无图发送、缩略图、undo/delete 清图行为不变。

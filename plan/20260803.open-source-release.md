# 开源发布：净化本仓库并推送 GitHub 公开仓库

> **文档定位**：**活 spec**（会随实施反复更新）。§5「关键决策与未决项」是唯一真相源，正文引用它、不复述它。

## 0. 一页纸（骨架先行）

- **一句话**：这不是"加个 LICENSE 就 push"，而是把一个**默认零鉴权、硬编码本机基础设施、且在 patch 文件里逐字分发 Cursor 专有代码**的自用仓库，改造成陌生人能安全跑起来的公开项目。

- **承重决策**（每条一句结论 + 一句为什么，细节挂后文）：
  1. **新建 GitHub 公开仓库，从 orphan 初始提交起步，历史不迁** —— 现有 95 条历史里 `config.json` 被跟踪过 7 个版本、泄露 20+ 私有项目绝对路径，另有 10 个提交署公司邮箱；squash 一次性解决，比 filter-repo 省事且更彻底（详见〈决策·orphan-export〉）。
  2. **不 clone 新目录，就地加 remote** —— SDK 会话历史按 workspace 绝对路径寻址，当前路径下有 530MB 数据，换目录等于让它全部失联（详见〈决策·in-place-remote〉）。
  3. **鉴权走 cookie，不走 Authorization header** —— 前端有三类浏览器原生加载（SSE、TTS 音频、用户图片）根本无法携带自定义 header，cookie 是唯一能同时覆盖三者的载体；企微桥同读 `AUTH_TOKEN`、请求带 Cookie（详见〈决策·cookie-token〉〈决策·wecom-auth-cookie〉）。
  4. **升级到 `@cursor/sdk@1.0.26`，只保留 patch 1&2，改 postinstall 正则注入并删 patch 文件** —— 1.0.26 仍未修 stall 吞 completion 与 Shell cwd 错绑；team repos 那条上游已部分缓解故不带走。原 patch 1.8MB 逐字分发 SDK 构建产物，公开不合规；注入只描述改动点、失配非零退出（详见〈决策·sdk-upgrade-1.0.26〉〈决策·patch-scope-1-2〉〈决策·regex-inject-patch〉）。
  5. **README 必须声明：唯一的安全边界是"谁能访问这个网页"** —— folders 白名单与 realpath 禁锢约束的是"在哪开会话/UI 能浏览什么"，而 agent 跑在 LocalExecutor 里能执行任意 shell、可触达整个文件系统与全部凭据。不写透这一点，读者会以为有沙箱从而放心暴露公网（详见〈决策·no-sandbox-disclaimer〉）。

- **验收总目标**：在一台干净环境上 `git clone` 公开仓库 → `npm i`（装上 1.0.26 并自动注入 patch 1&2）→ 复制 `config.example.json` 改 folders → 填 `CURSOR_API_KEY` → `npm start`，能新建会话、跑完一轮带工具调用的对话且收敛到终态（不卡 RUNNING）。这是"别人能跑起来"的唯一判据。

### 1.2 背景与动机

本仓库是单用户自托管的 Cursor SDK 网页前端，一切设计前提都是"只有我一个人、在我自己的内网、用我自己的基础设施"。开源要打破的正是这三条前提：陌生人没有你的 llm-proxy、会把服务暴露在你预料不到的网络位置、也不会读代码注释才知道边界在哪。

### 1.3 目标与验收标准

见 §0「验收总目标」。分解到子任务的验收在 §4.1。

### 1.4 约束与前提

静态前提（不会变，就地写满）：

- 运行时形态不变：主对话仍是单进程 Express + tsx；企微桥接为**另一进程**（`src/wecom/`，只经 HTTP 调主服务）。无构建步骤，前端仍是无打包器的原生 ES 模块。开源不引入构建链。
- 依赖纪律：运行时依赖为 `express`、`@cursor/sdk`、`ws`（企微 WS 客户端）。本次改造**不因此再增**运行时依赖——cookie 解析手写十几行即可，不引 `cookie-parser`。
- 目标受众是"能读中文、会配 Node 环境、自己有 Cursor API key 的个人开发者"，不是普通消费者。不做安装向导、不做 Docker 镜像（可后续）。

会随实施确认或可能翻盘的约束（只点到，权威结论在 §5）：SDK 升到 1.0.26 且只注入 patch 1&2（〈决策·sdk-upgrade-1.0.26〉〈决策·patch-scope-1-2〉）、暂不做英文化（〈决策·no-i18n〉）、许可选 MIT（〈决策·license-mit〉）。

## 3. 方案设计

### 3.1 仓库形态

**方案 A：一次性净化后 orphan 导出，此后单仓开发（选定）**

在当前私有仓库就地做完全部净化，验证通过后造 orphan 初始提交推到 GitHub，开发主战场转到公开仓库，原私有仓库归档不动。私有内容靠现有 `.gitignore`（已覆盖 `config.json`/`.env`/`data/`/`models-catalog.json`）天然隔离。

**方案 B：私有仓库继续开发，脚本剥离后单向同步**：私有仓库不受约束可继续随手写私有引用，但要长期维护剥离脚本、外部 PR 无法自然回流、`AGENTS.md` 事实上要维护两份且会漂移。

选 A：用户已明确"后续逐渐使用该仓库做迭代"，B 的双轨成本会一直付；而那些私有引用清掉后自用没有损失——它们对理解代码没有贡献。

### 3.2 配置解耦粒度

**方案甲：只解耦"不解耦就跑不起来"的项（选定）** —— llm 段、tts 段、模型白名单三处，其余照旧，`config.ts` 的 `loadFolders`/`addFolder` 写盘逻辑不动，回归风险低。

**方案乙：建统一配置层**（env 优先 + `config.json` 兜底 + schema 校验 + 启动打印生效配置）对新用户最友好，但 `config.ts` 要重写，folders 读写有回归风险，工作量 L。

选甲：目标是让别人跑起来，不是造配置框架；乙的收益要在配置项很多时才体现，而本项目配置项就那么几个。

### 3.3 执行步骤

受一条总原则支配：**可失败、可回滚的动作全部前置，不可逆的对外动作殿后。** 唯一不可逆的是"推到公开仓库"——一旦 push，泄露就召不回来了。

1. **先做全部代码与文档改动**（§4.1 任务 1~8），每步都能 `git reset` 回退。
2. **本地全量验证**：`npm run typecheck` + 手动跑通一轮对话 + 鉴权四种组合（见 §4.2）。
3. **临时净化复查**：`git ls-files` 列出最终清单，逐眼确认不含 `config.json`、`.env`、`data/`、`patches/`、两份文档镜像、`ai-traffic-capture.md`；再全库搜一遍 private-git 地址、skills 路径、`local-bridge`、真实 agent id。**这一步不通过就不许进下一步。**
4. **造 orphan 提交并推送**（不可逆，最后做）：`git checkout --orphan release` → `git add -A` → 一条初始提交 → `git remote add github git@github.com:wolf-joe/cursor-web-chat.git` → 推到 `main`。`[已验证: git 标准用法]`
5. **冷启动验收**：临时 clone 到 `/tmp` 模拟新用户走完 §0 验收总目标，完成后删除临时目录，并清掉 `~/.cursor/projects/` 下因此新增的 workspace 条目。
6. **切换主战场**：把 `github` 设为 `origin`，原私有 remote 改名归档保留。

### 3.4 压力测试

只保留"暴露了新设计点 / 不显式兜底就会出事"的行。

| 维度 | 场景 | 表现 | 防御性设计 |
|---|---|---|---|
| 演进 | SDK 未来版本重构掉 patch 1/2 锚点 | 若脚本"找不到就跳过"，安装与启动全部正常，但工具调用会永久卡 RUNNING 或 Shell cwd 错绑——**静默是这里最坏的失败模式** | 任一条注入失配必须非零退出让 `npm install` 失败，并打印指向 `docs/cursor_sdk_patches.md` 的说明。见〈决策·regex-inject-patch〉 |
| 操作 | 本机从 1.0.23+三补丁迁到 1.0.26+仅 1&2 | 丢掉 patch 3 后，dashboard `getTeamRepos` 瞬时失败时**当前那一次**工具仍可能 STOPPED（上游已清 rejected 缓存，同轮后续可重试，不再连环全挂） | README「本机迁移清单」写明；可接受则按〈决策·patch-scope-1-2〉不带走 |
| 操作 | 从主屏 PWA 冷启动 | session cookie 会导致每次启动都要重输 token（manifest 的 `start_url`/`scope` 均为 `/`） | cookie 设显式 Max-Age（30 天量级） |
| 操作 | http 局域网访问 | 若 cookie 默认标 `Secure`，浏览器根本不写入，表现为"输对 token 也一直跳回登录页"，几乎无法自查 | 默认不标 Secure，给 https 部署留开关，README 写明 |
| 操作 | 你自己的部署跟着升级 | TTS 默认关闭 + 白名单移入 `config.json`，你现有 `config.json` 缺这两段 → 朗读按钮消失、模型选择器变成账号全量目录；若开了 `AUTH_TOKEN`，企微桥裸 fetch 会被拦 | README 单列「本机迁移清单」；桥接按〈决策·wecom-auth-cookie〉带 Cookie |
| 操作 | 配了 `AUTH_TOKEN` 后跑企微桥 | 桥接不带凭证 → chat/stream/cancel 全被中间件拒，表现为企微无回复、难自查 | 桥接与主服务读同一 `AUTH_TOKEN`，请求显式带 `Cookie`；未配 token 时行为与现在一致。见〈决策·wecom-auth-cookie〉 |
| 故障 | 陌生人没有 llm-proxy | 标题/commit 草稿/TTS 三个短任务全部报错 | 缺配置时降级：标题回退为用户首句截断、commit 草稿不可用但不阻塞提交、朗读按钮不渲染 |

已排除的维度：规模压力（单用户）、成本风险（无付费 API 批量调用）。

关于鉴权保护范围的压测结论：manifest 与 icons 被中间件一起保护是**可行的**——SW 注册写在 `app.js` 内（登录后才执行），未登录时 PWA 冷启动落到登录页正是想要的行为。因此中间件只需给登录页自身与验证接口开白名单，不必为静态资源逐个开洞。企微桥不走浏览器，不增加白名单洞口——靠同 token 的 Cookie 过中间件。

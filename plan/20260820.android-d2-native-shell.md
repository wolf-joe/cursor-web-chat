# 安卓薄壳 D2：锁屏提醒与流式 TTS

> **文档定位**：**活 spec**（会随实施反复更新）。「关键决策与未决项」表是唯一真相源；正文引用它、不复述它。

## 0. 一页纸（骨架先行）

- **一句话**：手机锁屏后浏览器保不住长连接和播放；用安卓薄壳把 **run 直播** 和 **TTS 出声** 收到原生前台服务里，网页仍负责对话 UI。这样结束时能在本应用通知，朗读能在锁屏听完，且以后加前台语音不必推翻这一层。

- **承重决策**（权威结论见 §5）：
  1. **表现层继续是现有网页（WebView）**，不重做 Compose 聊天 UI——系统能力会涨，气泡/工具卡/Overlay 不应双轨（详见〈决策·webview-ui〉）。
  2. **Kotlin 只做可替换的 Session**，不把 UI 写进 Service：先落地 `RunSession` + `TtsSession`，`VoiceSession` 只留接口、本迭代不做（详见〈决策·session-modules〉）。
  3. **TTS 走现有 PCM SSE（D2）**，锁屏也要第一块就出声，不用「等整段 wav」（详见〈决策·tts-pcm-native〉）。
  4. **进行中 / 朗读中各一个前台服务、通知栏常驻**（API 26+），换安卓后台资格；完成时改成本应用一条结束通知，不推飞书（详见〈决策·fgs-split〉〈决策·min-sdk〉〈决策·fgs-notify〉）。
  5. **只做安卓**；电脑浏览器另做回到前台对齐，不挡本壳（详见〈决策·android-only〉〈决策·web-visibility-reattach〉）。

- **验收总目标**：在已给「无限制耗电」的安卓真机上：锁屏后 run 仍能跑完并弹出本应用结束通知；锁屏后 TTS 能听完且可在媒体通知里暂停/继续；回到 App 后网页不再停在假「进行中」。电脑用法不回归。`VoiceSession` 不在本迭代验收。

## 1. 需求背景

### 1.1 原始需求

> 移动端切应用或锁屏后，网页仍显示进行中/停止按钮，但会话可能已继续甚至结束，只有强制刷新才看得到结果。电脑 `127.0.0.1` 很少遇到。
>
> 飞书每次结束都推干扰太大，且和网页不是同一应用、体验割裂。
>
> TTS 播放时手机并不持续亮屏；锁屏超过一段时间声音会断，界面出现 Network error。
>
> 「锁屏也要被提醒 / 也要听完」是硬需求。只考虑安卓。进行中通知栏常驻可以接受。后续可能前台常听麦克风，把语音变成会话输入或 TTS 暂停/继续——方案要为这留扩展性。选定 **D2**（薄壳 + 原生消费 PCM SSE），不上全量原生 UI。

### 1.2 背景与动机

硬需求的本质是操作系统能力，不是再优化一遍 EventSource。Screen Wake Lock 在页面不可见时会被丢掉；WebView/`fetch` 流式 PCM 在锁屏后会被掐，于是 TTS 打出 `Network error`。飞书能戳人，但通道错了。薄壳把「连」和「听」交给系统承认的前台服务，提醒留在本应用里。

### 1.3 目标与验收标准

见 §0；可勾选条目见 §4.2。

### 1.4 约束与前提

- 不改 `@cursor/sdk` Agent 主循环、不另开第二套会话协议（静态前提）。
- 复用现有 HTTP：`POST /api/chat`、`GET /api/agent/stream`、`POST /api/tts/stream`、`GET /api/tts/:runId`、`GET /api/conversation`（字段以源码为准，详见〈决策·reuse-http〉）。
- 单用户、侧载 APK；不接应用商店审核作为本迭代门槛。
- 厂商省电白名单由使用者在 MIUI 上开一次，文档说明即可，代码保证不了（详见〈决策·oem-battery〉）。
- 前台常听麦 **不在本迭代实现**，只约束模块边界（详见〈决策·voice-later〉）。
- Run / TTS 两个前台服务、最低 API 26（详见〈决策·fgs-split〉〈决策·min-sdk〉）。

## 2. 现状分析

### 2.1 相关代码/系统现状

- **直播**：`runHub` 独立消费 `run.stream()`，多订阅者；接入时补 `attach` + 重放 backlog + 尾巴；终态后极短宽限再销毁。`GET /api/agent/stream` 有事件才 `write`，**无注释心跳**。前端 `EventSource` 只绑 `onmessage`，无 `onerror` 重挂，无 `visibilitychange` 对齐。`state.streaming` 要收到 `done` 才清，所以僵尸连接会一直显示「停止」。
- **鉴权**：`AUTH_TOKEN` 走 HttpOnly cookie `cwc_auth`（`src/auth.ts`）。EventSource / 音频 / 图都不能带自定义 header，原生 OkHttp 必须与 WebView 共享这颗 cookie（详见〈决策·shared-cookie〉）。
- **TTS**：未缓存时 `POST /api/tts/stream` 推 `{type:status|audio|done|error}`，`audio.data` 为 pcm16le mono base64；采样率与后端 `ttsService` 一致。缓存命中走 `GET /api/tts/:runId` wav。网页首播用 `fetch` + Web Audio，锁屏后 `fetch` 失败即用户所见 Network error。`keepAwakeWhileTts` 用 Screen Wake Lock，且要求 `document.visibilityState === "visible"`，锁屏后必然释放——这是 API 契约，不是开关没生效。
- **PWA**：`manifest.webmanifest` + 透传 `sw.js`，没有 Media 前台服务，加到主屏幕达不到硬需求。
- **监听**：服务默认 `127.0.0.1`，手机要用已对局域网/HTTPS 放开的入口（Caddy 等）。壳内 WebView 的 origin 必须可配置（详见〈决策·server-origin〉）。

### 2.2 问题定位

- **类型**：平台能力缺口（需求缺失），不是 run 没跑完。
- **根因**：锁屏后 WebView 不是合格的长连接/媒体宿主；结束感知绑在同一条已死的 SSE 上。

### 2.3 现状与目标的差距

| 现状 | 目标 |
|------|------|
| 直播只活在页面 EventSource | 锁屏时由 `RunSession` 持有同一 SSE |
| TTS 首播绑在页面 `fetch` | `TtsSession` 在 `mediaPlayback` 服务里播 PCM |
| 结束感知 = 网页叮咚 | 本应用通知；回到前台网页与终态一致 |
| 无安卓工程 | `android/` 薄壳，UI 仍是 `public/` |

### 2.4 影响范围

- **新建**：`android/`（Gradle 应用：WebView Activity、Session、FGS、通知、窄 JS 桥）。
- **修改**：`src/server.ts` 给 agent/TTS 两条 SSE 加注释心跳；`public/stream.js` 回到前台对齐；`public/ttsPlayer.js` 在壳内把播放委托给原生（桌面路径保持 Web Audio / `<audio>`）。
- **可选**：`AGENTS.md` 一行指向本文；`.gitignore` 忽略 `android` 构建产物。
- **不改**：Agent 循环、企微桥、飞书、全量原生聊天气泡。

## 3. 方案设计

### 方案 D2：WebView UI + 原生 Session（选定）

- **思路**：Activity 加载已配置的服务 origin。网页照常发消息、画气泡。壳检测到 `window.CwcNative` 后：live run 由 `RunSession` 再用 OkHttp 订一份 `/api/agent/stream`（与页面 EventSource 并存，hub 本就支持多订阅者）；播放走 `TtsSession` 消费 `/api/tts/stream` 的 PCM，MediaSession 露出暂停/继续。run 进行中、朗读中各挂自己的前台通知（两个 FGS，见〈决策·fgs-split〉）；`done` 换成结束通知并 `evaluateJavascript` 让页面 refetch。`VoiceSession` 空实现，指令将来直接打 `TtsSession.pause/resume` 和 `submitText`。
- **改动范围**：见 §2.4。
- **优点**：硬需求可达标；UI 不双轨；语音扩展加在 Session 上，不必先重写前端。
- **缺点**：要维护 APK；WebView 与原生终态要对齐；双路 SSE 浪费一点流量（单用户可接受）。
- **工作量**：M～L。

### 方案 E：全量原生 UI（未选）

系统集成最好，但工具卡、diff、文件浏览与后续网页能力全部双轨。语音并不要求气泡是 Compose。本迭代不选；Session 边界留下，将来只换表现层。

### 方案 A/B/C：PWA / TWA / 只保活 WebView（已排除）

达不到锁屏提醒与听完。不展开。

### 方案对比

| 维度 | D2 | E |
|------|----|---|
| 锁屏提醒 / 听完 | 可以 | 可以 |
| 对话 UI | 复用 `public/` | 重做 |
| 以后加麦 | 加 `VoiceSession` + 桥 | 更顺，但已付 UI 成本 |
| 工作量 | M～L | XL |

### 最终选定

**D2**（用户 2026-08-20）。电脑侧「回到前台对齐」一并做，避免桌面切标签仍假进行中。

### 执行步骤

原则：**先让服务端心跳与网页可见性对齐可单独验收，再做壳；壳内先 Run 通知，再 Tts 锁屏播放；桥保持窄。**

1. **SSE 心跳** —— agent 与 TTS 两条流定期写 SSE 注释行，避免网关/NAT 空闲掐线。原生锁屏和网页重连都吃这一行，所以放在壳之前。
2. **网页 `visibilitychange` / `pageshow`** —— 仍 `streaming` 则拉 `/api/conversation`：无 `liveRun` 则当终态画完并清停止按钮、补叮咚；仍有则关掉僵尸 EventSource 再 `attachToStream`。电脑不装 APK 也能好一截。
3. **`android/` 工程骨架** —— 可配置 origin、WebView（DOM storage、第三方 cookie 按 HTTPS 实际需要）、登录后从 `CookieManager` 灌 OkHttp（HttpOnly 读得到）。
4. **`RunSession` 独立 FGS**（`dataSync` 或平台等价 type）—— 与 Tts 拆开（〈决策·fgs-split〉）。页面 `attachToStream` / `liveRun` 时由桥 `watchRun(agentId)` 拉起；心跳+断线重连；`done` 结束通知 + 通知网页 refetch；用户划掉通知不等于 `cancel`（取消仍走现有停止按钮 → `/api/agent/cancel`）。
5. **`TtsSession` 独立 FGS**（`mediaPlayback`）—— 壳内点击朗读走桥，原生 POST PCM SSE，AudioTrack/ExoPlayer 播 pcm16le；MediaSession 暂停/继续；`done` 后若已有 wav 可切缓存以便以后拖动（与网页〈决策·seek-after-cache〉同语义）。桌面不走桥。最低 API 26（〈决策·min-sdk〉），FGS type 按 API 34 行为编写、低版本走兼容路径。
6. **窄桥 `CwcNative`** —— 仅 `watchRun` / `unwatchRun`、`ttsPlay` / `ttsPause` / `ttsResume` / `ttsStop`、`onRunTerminal` 回调进 JS。禁止每加一个功能就 `eval` 一大段 DOM 操作。
7. **文档** —— 真机：通知权限、无限制耗电、自启动；不把密钥写进 APK。

### 压力测试（只留不显式兜底会出事的）

| 压力维度 | 具体场景 | 方案表现 | 防御 |
|----------|---------|----------|------|
| 故障容错 | WebView 冻死、原生仍连着 | 通知能出，打开仍可能假进行中 | `onRunTerminal` + 可见性 refetch 必须落地 |
| 故障容错 | 双路 SSE 一个已 `done`、一个还在重连 | 网页可能晚一拍 | 以 `/api/conversation` 的 `liveRun` 为准，不以 EventSource 记忆为准 |
| 操作风险 | HttpOnly cookie 没进 OkHttp | 原生 401，通知永远没有 | 登录成功、每次 resume 从 CookieManager 同步 |
| 演进 | 以后加前台麦 | 若把播放写死在 Activity | Session 独立；Voice 只调 TtsSession 与 `submitText` |
| 厂商 | MIUI 杀 FGS | 硬需求失败 | 〈决策·oem-battery〉说明；无法代码兜死 |
| 成本 | 无新的按量 API | 沿用现有 TTS/LLM | 无首跑付费闸门 |
| 外部契约 | PCM 格式 | 与 `TtsSseEvent` 不一致则杂音/崩溃 | 实施时对照 `src/ttsService.ts` 的 `TtsSseEvent` 与采样率，禁止凭记忆写死 |

## 4. 实施计划

### 4.1 子任务拆解

| # | 任务 | 涉及文件/模块 | 验收标准 | 优先级 |
|---|------|---------------|----------|--------|
| 1 | SSE 注释心跳 | `src/server.ts` | agent/TTS 流在无业务事件时仍有定期注释；网页与 OkHttp 都不当业务事件解析 | 必须 |
| 2 | 网页可见性对齐 | `public/stream.js` 等 | 锁屏再打开：已结束则不再显示停止；仍在跑则能继续刷工具/思考 | 必须 |
| 3 | 安卓工程 + origin + 共享 cookie | `android/` | 能打开现网、登录一次后原生请求带 `cwc_auth` | 必须 |
| 4 | RunSession + 结束通知 | `android/` + 窄桥 | 锁屏期间 run 结束 → 本应用通知；点通知进同一会话且 UI 已终态 | 必须 |
| 5 | TtsSession PCM + 媒体通知 | `android/` + `ttsPlayer.js` 委托 | 锁屏能听完；媒体控件可暂停/继续；断流有明确错误而非卡住 | 必须 |
| 6 | VoiceSession 占位 | `android/` | 空模块或接口文件，无麦权限、无常听逻辑 | 应该 |
| 7 | AGENTS.md / gitignore | 仓库根 | 指向本文；不提交 build | 应该 |

### 4.2 测试要点

- [ ] 电脑：切标签再回来，直播能续或已结束能看到终稿（任务#2）。
- [ ] 安卓前台：行为与现网一致（发消息、工具卡、停止仍取消 run）。
- [ ] 安卓锁屏：run 结束有本应用通知，不是飞书。
- [ ] 安卓锁屏：TTS 听完；暂停/继续可用。
- [ ] 回到 App：没有假「进行中」。
- [ ] 用户点停止：run 真 cancel，通知收掉。
- [ ] 未装壳的桌面浏览器：TTS 仍走网页播放器。
- [ ] 登录失效：原生不静默假成功。

### 4.3 首跑策略

**触发判断**：否（不新增付费调用；TTS 仍是用户主动点朗读）。

# 企业微信智能机器人桥接（MVP）

> **文档定位**：活 spec（会随实施反复更新）。「关键决策与未决项」表是唯一真相源，正文引用它、不复述。
>
> **外部文档**：企微智能机器人长连接 [path/101463](https://developer.work.weixin.qq.com/document/path/101463)（已验证拉取；本地 HTML 快照非必需）。

## 0. 一页纸（骨架先行）

- **一句话**：独立进程把企微单聊接到现有 `cursor-web-chat` HTTP API，固定 cwd 上续聊/新建 agent，用一条流式气泡回推 thinking + 工具名/参数 + 正文。
- **承重决策**：
  1. **方案 A 薄桥接** —— 桥接只做企微 WS + 指令 + 投影；agent 一律 HTTP 调网页服务。因为 busy/cancel/runHub 是进程内状态，双进程直连 SDK 会竞态（详见 §3 / 〈决策·http-drive〉）。
  2. **长连接流式** —— `aibot_respond_msg` + `msgtype=stream`，同 `stream.id` 全量替换。因为官方长连接无轮询刷新，且匹配「边生成边刷」（详见 〈决策·wecom-stream〉）。
  3. **单气泡投影** —— thinking / 工具（仅 name+可截断 args）/ 回复压进同一条流式 content。因为企微侧只要可读过程，不要工具 status/result（详见 〈决策·transcript-one-bubble〉）。
  4. **指令极简** —— `new` 解绑不删；`stop` → cancel；busy 拒普通消息。会话列表/撤销仍走网页端（详见 〈决策·commands-mvp〉）。
  5. **cwd 启动可配** —— CLI/`env` 钉死，且必须落在 `config.json` 的 `folders` 白名单（详见 〈决策·cwd-cli〉）。
- **验收总目标**：单聊文本能在固定 workspace 续聊并流式回推；`new`/`stop`/busy/非文本行为符合 §1.3；网页端可看到同一 agent 与直播；主对话 API 无回归。

## 1. 需求背景

### 1.1 原始需求

> 将本项目与企业微信机器人连通。用户和机器人对话相当于跟某一个文件夹对话；AI 有回复时通过企微消息发给用户。MVP：固定 workspace；AI 回复期间拒绝新消息；`new` 新开会话、`stop` 中断本轮；会话管理与撤销可在网页端做。参考企微智能机器人长连接文档。

### 1.2 背景与动机

手机/企微里随手问某个本地仓库，复用已有 local agent 与网页端会话资产，不另起一套 agent 运行时。

### 1.3 目标与验收标准

- [ ] 单聊文本 → 固定 cwd 新建或续聊；网页端可见同一会话，并可看到本轮直播。
- [ ] 企微同一条流式气泡内含【思考】、【工具】name+args、【回复】，并随生成节流刷新，结束时 `finish=true`。
- [ ] busy 时普通消息拒收并提示；`stop` 能中断本轮；`new` 后下一条为新会话（旧 agent 仍在网页列表，未删除）。
- [ ] 非 `text` 消息忽略并提示；群聊可忽略（MVP 只做单聊）。
- [ ] 流式刷新不因企微 30 条/分钟频控失败（节流生效）。
- [ ] 网页原有 chat / stream / cancel 行为无明显回归。

### 1.4 约束与前提

- 单用户自用；单聊为主（详见 〈决策·single-user-dm〉）。
- 桥接为**独立进程**（Supervisor 另开 program）；**如何部署不在本文范围**，只约定进程边界与 HTTP 依赖（详见 〈决策·separate-process〉）。
- 凭证：`WECOM_BOT_ID` / `WECOM_SECRET`（及可选 base URL）走 env / 启动参数，不进 git（同 `CURSOR_API_KEY` 惯例）。
- 静态前提：现有服务 Express + `POST /api/chat`、`GET /api/agent/stream`、`POST /api/agent/cancel`；模型默认用网页服务已有 `MODELS_CONFIG.default`。

## 2. 现状分析

### 2.1 相关代码/系统现状

- **发消息**：`server` 的 `POST /api/chat` → `agentService.sendMessage` → `runHub.startRun`；无 `agentId` 即新建。
- **busy**：`agentCache` 条目上的进程内 `busy`；冲突抛 `AgentBusyLocallyError` → HTTP 409。
- **取消**：`cancelRun` 调内存里的 `currentRun.cancel()`；无进行中 run 则失败。
- **直播**：`runHub` 独占消费 `run.stream()`，SSE 扇出；`assistant` 文本块为增量（前端 `stream.js` 累积）；另有 `thinking`、`tool_call` 等事件。
- **cwd**：`config.json` → `folders[]`；磁盘作用域 API 只认白名单。
- **无**：企微适配、userid→agent 绑定、桥接进程入口。

### 2.3 现状与目标的差距

| 现状 | 目标 |
|------|------|
| 仅浏览器 UI 驱动对话 | 企微单聊经桥接驱动同一套 API |
| 无企微 WS / 流式回推 | 长连接 + `aibot_respond_msg` 单气泡节流刷新 |
| 无跨通道会话指针 | 持久化「当前 agentId」；`new` 解绑 |
| busy/cancel 仅网页按钮 | 桥接映射拒收 / `stop` |

### 2.4 影响范围

- **新建**：企微桥接入口与模块（建议 `src/wecom/` 或仓库约定的 bridge 入口文件）、binding 落盘、CLI。
- **可能轻改**：若缺「健康检查 / 显式 busy 查询」可补只读接口；**默认不改**主链协议，靠 409 与 cancel 语义即可。
- **不改**：网页会话列表/改名/删除/undo；agent 主循环与 `runHub` 语义；部署脚本细节（本文不写 Supervisor 安装步骤）。
- **跨系统**：无内部其它仓；外部仅企微智能机器人长连接 API。

## 3. 方案设计

### 方案 A：薄桥接（选定）

- **思路**：独立 Node 进程维持企微 WebSocket；收到文本后 HTTP 调现有服务；订阅 SSE，投影为一条企微 stream 全文并节流推送；指令本地处理。
- **改动范围**：见 §2.4；主服务以复用为主。
- **优点**：复用 busy/cancel/直播；网页与企微同看一轮；回归面小。
- **缺点**：SSE→企微投影与前端有少量重复；须自管心跳/重连/节流。
- **工作量**：M

### 方案 B：服务端投影 API（未选）

桥接更薄，但要新增 `stream-text` 类协议并养护，MVP 偏重。

### 方案 C：官方 `aibot-node-sdk` + 薄桥接（未选为默认）

协议层可少自研，但 SDK 分发/用法未在本仓验证。实施期若试装顺利，允许将 WS 骨架换成 SDK，**产品语义仍同方案 A**（详见 〈未决·aibot-node-sdk〉）。

### 方案对比

| 维度 | A 薄桥接 | B 服务端投影 | C 官方 SDK |
|------|----------|--------------|------------|
| 主服务改动 | 几乎无 | 新投影 API | 几乎无 |
| 回归风险 | 低 | 中 | 低（SDK 风险外置） |
| MVP 合适度 | 高 | 一般 | 可作为 A 的 WS 实现替换 |

### 最终选定

**方案 A**。驱动方式、气泡内容、工具字段已确认（详见 §5）。

### 执行步骤

原则：先连通回声，再接 agent，最后投影与边界。

1. **企微 WS 骨架** — 连 `wss://openws.work.weixin.qq.com`，`aibot_subscribe`，30s `ping`，断线重连；先对文本做固定回声，验证凭证与单聊通路。因为协议与鉴权失败应与 agent 问题隔离。
2. **指令与过滤** — 按 〈决策·commands-mvp〉 处理 `new`/`stop`、非 text、非单聊、`msgid` 去重。因为这些不依赖主服务。
3. **HTTP 驱动** — `POST /api/chat`（带 binding 的 `agentId` 或省略以新建）→ `GET /api/agent/stream` → 需要时 `POST /api/agent/cancel`；`--cwd` / `--base-url`（详见 〈决策·cwd-cli〉 / 〈决策·http-drive〉）。因为必须落在已有 busy/runHub 语义上。
4. **binding 落盘** — 记住当前 `agentId`；`new` 清空；进程重启可续（详见 〈决策·binding-file〉）。
5. **投影 + 节流流式** — 按 〈决策·transcript-one-bubble〉 / 〈决策·stream-throttle〉 累积并 `aibot_respond_msg`；`done` 时 `finish=true`。
6. **边界兜底** — 10 分钟窗、长度截断、busy 文案、断线不续刷旧 `req_id`（详见 §3 压力测试与 §5）。

### 压力测试（残余风险 / 必做防御）

| 压力维度 | 具体场景 | 方案表现 | 防御性设计 |
|----------|---------|----------|------------|
| 频控 | SSE 高频增量 | 每次 respond 计 1 条，顶 30/分钟 | 〈决策·stream-throttle〉 |
| 时长 | run >10 分钟 | 企微流式窗关闭 | 〈决策·stream-deadline〉 |
| 长度 | 长 thinking + 多工具 | content 可能超隐式上限 | 〈决策·transcript-truncate〉 |
| 断线 | WS 断于 run 中 | 旧 `req_id` 不可再刷 | 不续刷；可提示看网页；run 仍由主服务跑完 |
| 并发 | 网页与企微同 agent | 共享 busy → 409 | 企微提示忙碌；`stop`/`new` 仍处理 |
| 主服务挂 | chat/stream 失败 | 无 agent 结果 | 立即向用户回错误文案 |
| 排重 | 重复 `msgid` | 双跑风险 | 短窗 `msgid` 去重 |

### 4.2 测试要点

- [ ] 无 binding 首句 → 新建 agent；网页列表出现；续聊带同一 id。
- [ ] 直播中企微气泡出现思考/工具/回复刷新；结束后不再更新。
- [ ] busy 发普通消息 → 提示；`stop` → 主服务 cancel；`new` → 解绑且不删。
- [ ] 图片/文件等非 text → 提示忽略。
- [ ] 人为加快推送间隔，确认节流后无频控报错。
- [ ] 网页同时打开该 agent：可见同一轮；一端 busy 时另一端发送被拒。
- [ ] 桥接重启：binding 仍在；企微重连成功（同 bot 单连接）。

### 4.3 首跑策略

**触发判断**：涉及企微外部 API（非付费按量，但不可随意刷生产会话）→ 是。

**首跑铁律**：

- [ ] 先用回声验证 subscribe/respond，再接真实 agent。
- [ ] 首次成功的 `aibot_msg_callback` / `aibot_respond_msg` 原始帧可择要留作 fixture（脱敏），便于离线改投影。
- [ ] 确认 `stream.content` 实际可接受长度后再调 〈决策·transcript-truncate〉 阈值。

## 附录 B：企微侧消息投影示意（非契约）

```text
【思考】
...

【工具】Shell
args: {"command":"..." }   # 可截断

【回复】
...
```

同一 `stream.id` 下每次推送均为当前全文；用户看到的是原地更新的一条消息。

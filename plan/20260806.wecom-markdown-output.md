# 企微桥接输出改造：全 markdown + 周期活动摘要

> **文档定位**：活 spec（会随实施反复更新）。「关键决策与未决项」表是唯一真相源，正文引用它、不复述。
>
> **前身**：`plan/20260801.wecom-bot-bridge.md`（MVP）。本文推翻其输出层的四条决策（〈决策·all-markdown〉），MVP 的进程边界、HTTP 驱动、指令语义、binding、cwd 白名单全部沿用不变。
>
> **外部文档**：企微智能机器人长连接 [path/101463](https://developer.work.weixin.qq.com/document/path/101463)。

## 0. 一页纸（骨架先行）

- **一句话**：把企微侧输出从「一条 stream 气泡承载全部内容」改成「周期性 markdown 活动摘要 + 结束时 markdown 终稿」，因为企微客户端对 stream 是固定速率逐字动画，延迟只跟推进去的字符量成正比，减量与换载体是唯一杠杆。
- **承重决策**：
  1. **全 markdown、一帧 stream 都不发** —— 打字机动画是 stream 独有的，10 分钟必须 finish 的窗口也是 stream 独有的；换成 markdown 后两个问题同时消失，`StreamPusher` 整个删掉（详见 〈决策·all-markdown〉）。
  2. **过程与正文分轨** —— 过程走 3 秒一条的活动摘要气泡，正文只在 run 结束时作为终稿发出。因为过程是可丢弃的、正文是不可丢弃的，两者共用一条气泡就必然互相挤占字节与注意力（详见 〈决策·digest-interval〉/〈决策·final-last〉）。
  3. **频控账本 + 终稿预留额度** —— 3 秒一窗是 20 条/分钟，撞不到 30 条/分钟，但会在约 50 分钟耗尽 1000 条/小时；账本过水位就拉长间隔，并给终稿硬留额度，让极端长任务退化成「进度变稀」而不是「正文发不出去」（详见 〈决策·digest-budget〉）。
  4. **地基已实测通过** —— 「同一个 req_id 能否连发多条 markdown」是整个方案的唯一支点（`stream` 的多帧是它自己的协议特例，推不出 markdown 也行）。2026-08-06 实跑连发 7 条全部 `errcode=0` 且到达，长文本瞬间整段出现、无逐字动画（详见 〈决策·multi-markdown-ok〉/〈决策·markdown-no-typewriter〉）。
- **验收总目标**：短问答只出 1~2 条气泡且正文瞬间出现、不再落后网页；40 分钟长轮次全程有进度、结束后正文照常送达且日志中不再出现「接近 10 分钟窗」；超 20480 字节正文分多条且代码块不被切坏；cancelled/error 有明确终态气泡；单轮 respond 次数有账本、不触发频控。

## 1. 需求背景

### 1.1 原始需求

> wecom bridge 不太行，所有内容全挤在一个卡片里，特别长轮次的场景会触发企业微信的长度限制。另外所有内容是通过流式传输的，在企业微信上有打字机的效果，但是打字机效果很慢，导致网页都出来内容了，企业微信还在慢吞吞的打印之前的内容。

补充需求（同一轮对话）：全 markdown 方案；企微侧不需要看 thinking 全文，但要能看到细粒度进度（思考 / 工具调用），按固定间隔把窗口内的活动汇总发送；正文改成 run 结束后一次性送达可以接受；活动摘要间隔 3 秒。

### 1.2 背景与动机

手机上用企微看一个长轮次时，实际体验是「网页早已出完，企微还在逐字打印几分钟前的内容」，且超过 9 分钟的轮次结果直接送不到。过程可见性本身是要保留的，问题在载体选错了。

### 1.3 目标与验收标准

- [ ] 正文送达不再有动画滞后（markdown 无逐字动画已实测，详见 〈决策·markdown-no-typewriter〉）。
- [ ] 超过 10 分钟、乃至 40 分钟的轮次，正文仍能送达；日志中不再出现「企微流式接近 10 分钟窗，强制结束」。
- [ ] 过程可见：默认每 3 秒一条活动摘要，含思考摘录与工具调用行（详见 〈决策·digest-interval〉）。
- [ ] 长正文按已验证的 markdown 20480 字节上限分片，不再自截断正文（详见 〈决策·final-chunk〉）。
- [ ] cancelled / error 结束时有明确终态气泡，不静默。
- [ ] 主服务 chat / stream / cancel 协议与 runHub 语义零改动。

### 1.4 约束与前提

- 桥接仍是独立进程、仍只经 HTTP 调主服务（沿用 MVP 的 `决策·http-drive`、`决策·separate-process`）。
- 输出通道只有一条：回调带来的 `req_id`。主动推送（`aibot_send_msg`）这条路已判死，不再作为兜底（详见 〈决策·send-msg-dead〉）。
- 指令语义（`help`/`new`/`stop`）、binding 落盘、cwd 白名单、msgid 去重全部不动。
- 企微频控与消息上限是硬边界（详见 〈外部契约·rate-limit〉/〈外部契约·markdown-limit〉）。

## 2. 现状分析

### 2.1 相关代码/系统现状

`bridge.ts` 收到文本 → `POST /api/chat` → 订阅 SSE；`TranscriptBuilder` 把 thinking 全文、每次工具调用的 name 与 ≤500 字符 args、全部正文拼成一份全文；`StreamPusher` 以 ≥2 秒的节流把这份全文**全量替换**推给同一个 `stream.id`，`done` 时 `finish=true`。另有一个 9 分钟计时器到点强制 finish，以及 WS 断线时的 `markAbandoned`（此后本轮再也发不出任何东西）。`help`/`new`/`stop` 的回复走 `quickStream`，即一条一次性的 stream 气泡。

### 2.2 问题定位

- **问题类型**：设计缺陷（载体选择），非代码 Bug。
- **根因**：企微客户端对 stream 消息做固定速率的逐字动画，延迟只与推进去的字符总量成正比，因此调节推送间隔无效——2 秒改成 500 毫秒只会撞频控，动画不会变快。而当前投影往这条动画气泡里塞的字符量远超必要：以 15 次工具调用估算，thinking 约 3000 字符 + 工具行约 3000 字符 + 正文约 2000 字符，用户真正想读的只占四分之一。
- **「长度限制」的真实归因**：企微侧没有任何 errcode 记录，日志里有的是「企微流式接近 10 分钟窗，强制结束」。`transcript.ts` 的 `CONTENT_MAX_BYTES = 18_000` 超限后会自己追加 `…(内容过长已截断)`，9 分钟计时器到点也会自己追加 `…(耗时接近企微流式上限)`。**两行都是本仓写进内容里的，不是企微拒收**，所以 `stream.content` 的真实上限至今未被触碰过。这条归因直接删掉了「按远小于 20480 的悲观阈值设计」这个伪需求。
- **一个未验证的分叉，方案有意绕开**：动画成本究竟是 ∝ 最终全文长度（客户端只对新增尾巴做动画）还是 ∝ 累计推送字节（每帧全量替换都重放）无法从外部断定。本方案不发 stream，两种情况下都成立，因此这个分叉不必查清。

### 2.3 现状与目标的差距

| 现状 | 目标 |
|------|------|
| 过程与正文挤在一条动画气泡 | 过程走摘要气泡、正文走终稿气泡，互不挤占 |
| 正文滞后 ∝ 全文字符量 | 正文瞬间出现（markdown 无动画） |
| 超 9 分钟本轮结果全丢 | 无流式窗概念，40 分钟轮次照常送达 |
| 18000 字节自截断正文 | 按 20480 分片，正文不截断 |
| 2 秒节流恰好顶在 30 条/分钟上限，无账本 | 显式频控账本，进度可丢、终稿预留额度 |
| WS 断线 → 本轮作废 | 无 stream.id 作废概念（能否续发取决于 〈未决·reqid-across-reconnect〉） |

### 2.4 影响范围

- **重写**：`src/wecom/transcript.ts`（拆成窗口摘要与终稿两个渲染器）、`src/wecom/bridge.ts`（改窗口驱动）。
- **删除**：`src/wecom/streamPusher.ts` 整体，连同 9 分钟 deadline 与 `markAbandoned`。
- **新增**：按 req_id 组织的输出通道模块（〈决策·reply-channel〉）。
- **小改**：`src/wecom/ws.ts` 加 markdown 发送；`AGENTS.md` 里描述企微桥接的那句「SSE 单气泡节流回推」需同步；`plan/20260801.wecom-bot-bridge.md` 的四条输出层决策标为已翻盘。
- **不改**：主服务任何路由、runHub、agentService、网页前端；企微指令语义与 binding。

## 3. 方案设计

### 方案 A：单气泡瘦身（未选）

保留一条 stream 气泡，砍 thinking、工具压成一行，正文仍走流式。减量 3~4 倍，工作量 S。但正文越长动画延迟越长，性质没变；10 分钟窗与断线依旧丢结果。

### 方案 B：stream 进度轨 + markdown 终稿（未选）

进度走 append-only 的 stream 气泡，正文走 markdown。正文延迟解决，但仍要养一套流式窗与放弃语义，而它换来的「原地刷新」只用在进度上——性价比不成立。

### 方案 C：方案 B + 续窗与断线恢复（未选）

9 分钟到点结束当前气泡、开新 `stream.id` 续窗。功能上最全，但把 stream 的复杂度又加深了一层。

### 方案 D：全 markdown（选定）

- **思路**：一帧 stream 都不发。周期性把窗口内的活动渲染成 markdown 气泡，run 结束时把正文作为终稿气泡（必要时多条）发出。
- **为什么它能解决 9 分钟问题**：10 分钟窗是 `stream` 这个 msgtype 自身的属性（自首帧起算），不是会话级约束；约束会话的是 24 小时回复窗。不发 stream，这个计时器就不存在。
- **顺带解决断线**：`markAbandoned` 存在的唯一原因是「重连后旧 stream.id 的帧作废」。markdown 是一次性投递的独立消息，没有这个概念——能否续发只取决于 req_id 本身是否还有效（详见 〈未决·reqid-across-reconnect〉）。
- **代价**：markdown 不能原地刷新，进度只能是离散气泡，颗粒度换成了气泡数量（详见 〈决策·digest-interval〉里的算术）。
- **工作量**：M。

### 方案对比

| 维度 | A 瘦身 | B 分轨 | C 分轨+续窗 | **D 全 markdown** |
|------|--------|--------|-------------|-------------------|
| 长正文动画延迟 | 仍 ∝ 正文长度 | 无 | 无 | 无 |
| 超 9 分钟轮次 | 丢结果 | 正文可达、进度断档 | 都不丢 | 无此概念 |
| 进度形态 | 原地刷新 | 原地刷新 | 原地刷新 | 离散气泡 |
| 需维护的 stream 复杂度 | 全部 | 全部 | 更多 | **零** |
| 工作量 | S | M | M+ | M |

### 最终选定

**方案 D**。stream 唯一的价值是原地刷新，而它恰好只用在过程展示上——而过程是可以接受粗颗粒、可以接受离散气泡的那一半。放弃 stream 后，流式窗、节流语义、放弃语义、只追加约束一并消失，净减代码。

### 执行步骤

总原则：**可失败的验证前置，不可回退的删除殿后**——stream 代码是唯一的退路，验证通过前不许删。

1. ~~**首跑验证外部契约**~~ — ✅ 2026-08-06 完成，四条契约全部有结论（详见 〈决策·multi-markdown-ok〉/〈决策·markdown-no-typewriter〉/〈决策·markdown-dialect〉/〈决策·reqid-across-reconnect〉）。工具与证据：`scripts/wecom-contract-check.mjs`、`data/wecom/contract-check/`。
2. **`ws.ts` 加 markdown 发送** — 报文形状 `body: {msgtype:"markdown", markdown:{content}}`，已由脚本实跑验证。`respondStream` 可以直接删（第 1 步通过后它不再是退路），但留到步骤 6 一起清，避免中途 typecheck 断裂。
3. **输出通道对象** — 把序号、频控账本、「进度可丢弃 / 终稿不可丢弃」的优先级收在一处。放在渲染器之前做，因为两个渲染器都要经它发送（详见 〈决策·reply-channel〉/〈决策·digest-budget〉）。
4. **两个渲染器** — 窗口摘要与终稿分开实现。分开而不是共用一个 builder，是因为二者的截断策略相反：摘要以可读性为先、该截就截；终稿以完整性为先、只许分片不许截（详见 〈决策·digest-window-cap〉/〈决策·final-chunk〉）。
5. **`bridge.ts` 改窗口驱动** — 3 秒定时器 + 空窗跳过；`done` 时**先取消定时器并丢弃未发窗口**再发终稿，因为定时器与 run 结束几乎必然撞上，不先取消就会出现「正文之后又冒出一条过程摘要」（详见 〈决策·final-last〉）。
6. **拆除 stream 遗留** — 删 `StreamPusher`、deadline、`markAbandoned`；断线行为按第 1 步实测结论定。放最后，因为前面每一步都可能需要它兜底。
7. **文档同步** — 见 §2.4 的小改项。

### 压力测试（只保留暴露了新设计点的行）

| 压力维度 | 具体场景 | 方案表现 | 防御性设计 |
|----------|---------|----------|------------|
| 规模压力 | 单个 3 秒窗内 50 次工具调用（批量改文件） | 单条气泡撞 20480 字节，服务端直接拒收 `errcode 40058` | 窗内也有字节预算，超出保留前若干步 + 一行「另有 N 步」（〈决策·digest-window-cap〉） |
| 规模压力 | 60 分钟轮次 × 3 秒节奏 | 20 条/分钟 → 约 50 分钟耗尽 1000 条/小时，终稿可能发不出去 | 小时预算水位退避 + 终稿硬留额度（〈决策·digest-budget〉） |
| 顺序 | run 在第 2.9 秒结束，定时器第 3 秒触发 | 用户先看到正文、再看到过程摘要 | 终稿前取消定时器并丢弃未发窗口（〈决策·final-last〉） |
| 长度 | 正文含未闭合代码围栏且需分片 | 切点落在围栏内 → 前片剩余全被当代码、后片不成形 | 优先段落边界切，跨片闭合并重开围栏，加 `(2/3)` 序号（〈决策·final-chunk〉） |
| 长度 | 分片计算按字符而非字节 | 中文 3 字节/字，按字符估算必然低估、撞 40058 被整条拒收（不是截断，是**整条不发出去**） | 分片一律按 `Buffer.byteLength` 计算（〈决策·final-chunk〉） |
| 隐私 | thinking 与 args 流向企微（外部系统） | 内部推理与本机绝对路径外泄面扩大 | 单用户自用可接受；摘要按窗截断而非全文，顺带压住外泄量（〈决策·digest-window-cap〉） |

## 5. 关键决策与未决项（唯一真相源）

### 5.1 已定决策 / 约束

| 名字 | 结论 | 来源 | 影响位置 |
|------|------|------|----------|
| 决策·all-markdown | 输出全部走 `aibot_respond_msg` 的 markdown；一帧 stream 都不发。推翻旧 plan 的 `决策·transcript-one-bubble`/`决策·stream-throttle`/`决策·stream-deadline`/`决策·transcript-truncate` | 用户 Phase 3 选定；根因见 §2.2 | §3、任务#1/#7 |
| 决策·digest-interval | 活动摘要默认每 **3 秒**一条；空窗不发（首窗若无活动发一条「收到，处理中…」，仅一次）。算术：3 秒 = 20 条/分钟，撞不到 30 条/分钟，但约 50 分钟耗尽 1000 条/小时；一个 10 分钟轮次约 200 条气泡 | 用户 Phase 3 指定间隔 | 任务#5、〈决策·digest-budget〉 |
| 决策·digest-budget | 显式频控账本：进度气泡可丢弃、终稿与指令回复不可丢弃并硬留额度；小时预算过水位后自动拉长间隔（阶梯值实施期定，见 〈未决·backoff-ladder〉） | 〈外部契约·rate-limit〉 + §3 压测 | 任务#2/#5 |

| 决策·final-chunk | 终稿只含正文，按 20480 **字节**（`Buffer.byteLength`，非字符数）分片；优先段落边界，跨片闭合并重开代码围栏，加 `(i/n)` 序号；**正文不截断** | 〈外部契约·markdown-limit〉 + §3 压测 | 任务#4 |

| 决策·send-order | 背靠背连发（实测间隔 150ms）到达顺序与发送顺序一致，终稿多片可直接顺序连发，无需等前一片 ACK | 实测 2026-08-06 ✅ | 任务#2/#4 |
